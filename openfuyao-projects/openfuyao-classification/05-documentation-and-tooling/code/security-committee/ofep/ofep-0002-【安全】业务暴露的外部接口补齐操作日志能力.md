## 概括

本提案要求所有对外部提供的接口补齐审计日志，以支撑安全回溯和合规审计。核心内容包括：

1. 明确审计日志适用范围（南北向外部接口）。
2. 规范审计日志字段格式（用户ID、时间、终端IP、业务模块、操作类型、操作结果、详细信息）。
3. 统一记录位置（与业务运行日志平行文件夹隔离）。
4. 推荐使用公共组件 `common-modules` 提供的 `seclog` 能力。
5. 特殊场景无法记录审计日志的接口需在文档中说明，并提交例外清单评审。

## 动机

### 背景

在安全合规场景下，审计日志是问题追溯、安全事件分析、合规检查的重要依据。当前 openFuyao 各业务模块对外部接口的审计日志记录存在以下问题：

- 部分模块未记录审计日志。
- 日志字段不统一，难以进行统一分析。
- 日志位置分散，不便集中管理。
- 部分敏感操作无法追溯。

### 设计动机

- **安全合规**：满足安全审计和合规检查要求。
- **问题追溯**：支撑安全事件分析和问题定位。
- **统一规范**：统一审计日志格式和记录方式。
- **可维护性**：使用公共组件，降低维护成本。

### 目标

1. 所有对外部提供的接口补齐审计日志记录。
2. 统一审计日志字段格式，满足安全回溯需求。
3. 统一记录位置，便于集中管理和分析。
4. 推荐使用公共组件 `common-modules` 的审计日志能力。
5. 无法整改的接口提交例外清单，经设计组评审确认。

### 非目标

1. 不在本提案中重构现有日志框架。
2. 不要求集群内东西向调用接口记录审计日志。
3. 不要求 K8s 原生资源和自定义资源（通过 APISERVER 访问）重复记录审计日志。

## 提案

### 方案一句话

使用公共组件统一审计日志格式，对所有外部南北向接口补齐审计日志，特殊场景提交例外清单评审。

### 核心决策

1. **适用范围**：仅外部南北向接口（暴露给 Web、三方系统、APP 的接口）。
2. **记录位置**：与业务运行日志平行文件夹隔离（如 `/var/log/seclog/<service>/operation.log`）。
3. **公共组件**：优先使用 `common-modules` 提供的 `seclog`，保持能力一致。
4. **例外处理**：无法整改的接口提交清单，经设计组例会评审确认。

### 用户故事

#### 故事 1：安全审计追溯异常操作

安全审计人员发现某个用户在凌晨执行了异常删除操作。通过查看审计日志，获取到用户ID、终端IP、操作时间、操作类型、操作结果等关键信息，成功定位问题源头，完成安全事件分析。

### 注释/约束/警告

1. **适用范围界定**：
   - **需要审计**：暴露给 Web 的接口、暴露给三方系统/APP 的南北向接口。增删改等改变了系统资源或者行为的操作，都需要记录日志。查询类操作，如果涉及敏感信息，也要记录。
   - **不需要审计**：集群内东西向调用、K8s APISERVER 访问的资源和自定义资源。

2. **敏感信息处理**：
   - 详细信息字段不得包含敏感信息（密码、密钥、个人隐私数据等）
   - 文字简短，记录操作关键信息

3. **公共组件使用**：
   - 优先使用 `common-modules` 的 `log` 和 `seclog`
   - 业务已有日志能力，建议本次统一整改掉，业务日志和操作日志分开记录
   - 公共组件仓库：[common-modules](https://gitcode.com/openFuyao/common-modules/blob/main/README.md)，readme中提供了使用说明。

4. **例外处理**：
   - 无法整改的接口需提交清单
   - 清单内容包括：模块名称、接口路径、无法整改原因、建议下游处理方式
   - 经设计组例会评审确认后方可例外

### 风险与缓解措施

| 风险             | 缓解措施                                                     |
| ---------------- | ------------------------------------------------------------ |
| 敏感信息泄露     | 详细信息字段不得包含敏感信息，代码审查把关                   |
| 日志存储膨胀     | 与业务运行日志平行隔离，归档、打包规格以公共组件的为准（公共组件已经实现） |
| 性能影响         | 异步写入日志，不阻塞业务逻辑                                 |
| 格式不统一       | 使用公共组件强制统一格式                                     |
| 无法整改接口遗漏 | 提交例外清单，设计组评审确认                                 |

## 设计细节

### 适用范围

#### 需要审计的接口

| 类型                 | 说明                         | 示例                                          |
| -------------------- | ---------------------------- | --------------------------------------------- |
| 暴露给 Web 的接口    | 用户通过控制台访问的业务接口 | `/rest/user/v1/users`, `/rest/alert/v1/rules` |
| 暴露给三方系统的接口 | 第三方系统调用的业务接口     | API Gateway 接口                              |
| 暴露给 APP 的接口    | 移动端 APP 调用的业务接口    | 移动端 API 接口                               |

#### 不需要审计的接口

| 类型               | 说明                     | 原因                                 |
| ------------------ | ------------------------ | ------------------------------------ |
| 集群内东西向调用   | 服务间内部调用           | 内部调用，认为是信任域内，暂不做要求 |
| K8s APISERVER 访问 | K8s 原生资源和自定义资源 | APIServer 已有审计日志               |

### 审计日志字段规范

| 字段         | 必填 | 说明                                 | 示例                               |
| ------------ | ---- | ------------------------------------ | ---------------------------------- |
| 用户ID       | ✓    | 操作用户的唯一标识                   | `user123`                          |
| 时间         | ✓    | 操作时间                             | `2026-04-29 10:30:00`              |
| 终端IP       | ✓    | 发起操作的客户端IP地址               | `192.168.1.100`                    |
| 业务模块名称 | ✓    | 当前操作所访问的资源或业务模块名称   | `user-management`, `alert-service` |
| 操作类型     | ✓    | 具体操作类型（新增、修改、删除等）   | `create`, `update`, `delete`       |
| 操作结果     | ✓    | 操作执行结果（成功、失败、异常等）   | `success`, `failed`, `error`       |
| 详细信息     | ✓    | 操作的详细描述信息，简短不含敏感信息 | `创建用户 user123`                 |

#### 日志格式示例

```json
{
  "userId": "user123",
  "timestamp": "2026-04-29T10:30:00Z",
  "clientIp": "192.168.1.100",
  "module": "user-management",
  "action": "create",
  "result": "success",
  "detail": "创建用户 user123"
}
```

### 记录位置规范

```
/var/log/seclog/
├── console-service/
       └── operation.log                 
├── user-management-operator/
       └── operation.log                 
├── alert-service/
       └── operation.log                 
```

**说明**：审计日志与业务运行日志平行文件夹隔离，便于统一管理和分析。

### 特殊场景处理

| 字段             | 说明                                 |
| ---------------- | ------------------------------------ |
| 模块名称         | 接口所属业务模块                     |
| 接口路径         | 接口的 URL 路径                      |
| 无法整改原因     | 无法记录审计日志的技术或业务原因     |
| 建议下游处理方式 | 提醒下游需自行补充记录审计日志的代码 |

### 功能启用和回滚

#### 如何启用/禁用此功能？

- 审计日志为合规要求，**不支持关闭**
- 例外接口需经设计组评审确认

- 不影响业务功能，仅增加日志记录

- 不可以。审计日志为合规要求，必须持续记录
