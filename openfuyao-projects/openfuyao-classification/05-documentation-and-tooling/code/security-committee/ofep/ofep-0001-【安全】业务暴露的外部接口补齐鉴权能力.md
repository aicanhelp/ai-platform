## 概括

openFuyao 核心组件和扩展组件在对外暴露的组件业务 API（在K8S原生的定义中，将此类资源统称为Non-Resource URL）存在的鉴权缺口：K8S的原生资源依赖 apiserver/karmada 能较好鉴权，但部分组件暴露的Non-Resource URL可能仅做转发未做鉴权，存在安全风险。

本提案在不破坏现网的前提下，补齐 Non-Resource URL 的统一鉴权能力：新增 Non-Resource 专属集群角色、引入“全局开关 + 服务规则”的策略模型，并将鉴权收敛到POD流量唯一入口（优先 oauth-proxy sidecar，次选应用 filter），支持热更新与可回滚的上线策略。

## 动机

### 目标

- 补齐 Non-Resource URL 的统一鉴权，避免组件暴露的API裸奔带来的安全风险。
- 新增集群级Non-Resource专属角色，完成只读/读写的语义分离：
  - cluster-nonresource-viewer
  - cluster-nonresource-editor
- 形成可平滑升级的统一策略模型：
  - 全局策略：是否启用Non-Resource URL鉴权
  - 服务策略：path+method 与角色的映射、内部豁免、历史兼容
- 支持配置热更新，无需重启进程即可生效。
- 上线默认不破坏历史调用链，升级环境默认关闭，提供灰度开启与可观测审计能力。

### 非目标

- 不重构 console-service 主路由框架与现有分流体系。
- 不重做业务功能权限模型，仅聚焦接口鉴权层（Non-Resource URL）。
- 第一阶段不强制将所有集群内东西向调用纳入统一鉴权，集群内东西向调用认为是内部调用，属于同一个信任域内
- 现阶段的平台级角色（2个）、集群级角色（3个）保持现状，本提案不对其进行整改。

## 提案

本提案的一句话方案：在外部流量入口统一执行 Non-Resource URL 鉴权，并通过“专属角色 + 开关项”实现从兼容到收敛的渐进式加固。

核心设计点：
- 新增两个 Non-Resource 集群角色，避免复用 cluster-viewer/cluster-editor 导致语义冲突。
- 策略采用双层配置：
  - 全局策略（单实例 ConfigMap）：控制是否启用鉴权模式。
  - 服务策略（每服务一份 ConfigMap）：声明可对外暴露的接口与访问角色要求，并定义内部豁免放行接口，确保与历史兼容。
- 执行点优先级：
  - P0：oauth-proxy sidecar（推荐）
  - P1：应用 filter（推荐）
  - P2：每个业务接口入口代码处（不推荐）
- 多集群链路不替代当前的转发逻辑，本提案补的外部请求“到达服务后端endpoint后的鉴权逻辑”。

### 用户故事

#### 故事 1

升级场景，从任意历史版本升级到 v26.06 后，默认不启用 Non-Resource URL 拦截；管理员可以在确认全部三方对接系统（如果有,之前可能是裸访问的，没有执行鉴权）都完成整改后再开启鉴权模式，避免已有的三方对接/集成访问中断。

#### 故事 2

全新部署的场景，没有历史包袱，也不存在已经完成和三方对接的组件，这种场景默认开启 Non-Resource URL 拦截，保证所有业务接口都做鉴权。

### 注释/限制/注意事项

- 鉴权逻辑必须在服务端入口执行（oauth-proxy/filter/入口代码），不依赖 ingress/web 层的鉴权结果。
- 防绕过要求：Ingress/Service 仅暴露鉴权入口端口，不允许旁路暴露业务容器端口。
- 服务监听要求：业务服务对外端口应绑定到 127.0.0.1 或指定 IP（配合 sidecar 入口），避免默认监听 0.0.0.0 形成旁路。
- 若服务无法使用 ConfigMap方式声明规则（例如鉴权逻辑历史上散落在入口代码中），必须补充一份“接口鉴权基线表”，内容与ConfigMap方式声明规则一致即可，用于测试验收与自查。

### 风险与缓解措施

- 风险：升级后强制鉴权导致历史三方调用中断。
  
  - 缓解：升级环境默认关闭；升级脚本中做实现，从任意版本升级到26.06时，ConfigMap中是没有authNonResourceURLs，此时默认赋值off。
- 风险：sidecar/路由暴露不当导致绕过鉴权入口。
  
  - 缓解：业务只开放鉴权入口给Service/Ingress，鉴权后再转发到业务代码；
  
  

## 设计细节

### 角色与权限模型

- 新增cluster-nonresource-viewer：只读访问受保护的 Non-Resource URL（GET）。
- 新增cluster-nonresource-editor：读写访问受保护的 Non-Resource URL（GET/POST/PUT/PATCH/DELETE 等）。
- 空实现：该角色不绑定任何权限，为了兼容和一致性，代码和之前的集群级角色实现方式一致。目的就是把user和新增的角色能做绑定。
- 与现有角色并存：cluster-admin / cluster-editor / cluster-viewer 不变；新增角色用于“业务接口资源角色”绑定。

### 策略模型与配置载体

全局策略（单实例全局一份 ConfigMap）建议字段：

```yaml
authNonResourceURLs: off # off | on  决定是否拦截，当前只提供这一个开关
```

服务策略（每服务一份 ConfigMap）建议字段：

```yaml
data:
  auth-rules.yaml: |
    # 要业务鉴权的接口， 采用restful标准格式，支持路径参数
    authRules:
      - path: /api/logs/
        methods: [GET]
        roles: [cluster-nonresource-viewer]
      - path: /api/info/
        methods: [POST, PUT, PATCH, DELETE]
        roles: [cluster-nonresource-editor]
        
    # 内部免鉴权接口，也就是没有开放给外部的，是开放给内部用的接口。使用serviceAccount身份就可以访问。使用user身份，就是从ingress来的接口，不应该访问这部分内容。
    authBypass:
      - path: /api/inner/
        methods: [GET]

    # 裸奔接口，某些业务场景下，无法整改的，先保留
    authLegacy:
      - path: /healthz
        methods: [GET]
```

匹配与决策逻辑：
- authNonResourceURLs=off：放行，行为与历史一致。
- authNonResourceURLs=on：
  - 命中 authRules：基于 path+method 找到 roles，调用 SAR 进行授权判定。
  - 命中 authBypass：仅允许来自集群内部、具备合法 ServiceAccount 身份的就放行。
  - 命中 authLegacy：保留历史兼容（原则上仅允许健康检查等无业务逻辑，直接return的接口）。
  - 以上均不命中：默认拒绝，并提示规则缺失。

对业务实现的建议

- 完全没有做过鉴权的建议使用configmap配置方式，通过filter或者auth-proxy
- 为了减少工作量，如果业务代码中已经有部分的鉴权逻辑，可以选择在现有的鉴权代码上做整改，但是要区分出来哪些接口要鉴权，哪些内部访问不需要鉴权。
- 不管是任何方式实现的，鉴权的逻辑都要在业务的服务端endpoint做鉴权，不能依赖web、ingress、service上的鉴权（即使其上有鉴权，也不能直接用鉴权结果）

### 热更新机制

- 全局策略与服务策略加载到内存。
- ConfigMap 中authNonResourceURLs变更触发策略热更新；生效无需重启进程，下一个请求使用新策略。
- 业务的configMap本质上只有升级的时候才会变化，非必要不用侦听。

### UI 交互变更（控制台）

- 集群角色：新增“业务接口资源角色”区域，包含 cluster-nonresource-viewer/editor；
- 增加总开关“启动业务资源鉴权”。
  - 全新安装默认开启。
  - 升级环境默认关闭。
    - 当前：任意版本升级到26.06版本，默认关闭authNonResourceURLs
    - 后续：任意版本，直接升级到26.06更高的版本，默认关闭authNonResourceURLs（因为没有经过26.06，等于是第一次看见这个特性，则默认关闭）
    - 后续：从26.06的版本（含）升级到任意更高版本，直接使用在26.06版本中已经保存的configMap中的authNonResourceURLs
- 集群成员：在现有集群角色之外，增加“业务接口资源角色”选择。
  - 默认选择cluster-nonresource-viewer。
  - 当集群角色选择 cluster-admin 时，默认关联选择cluster-nonresource-editor。

- 新装环境（部署脚本）：authNonResourceURLs=on。
- 升级环境（升级脚本）：
  - 若集群中不存在该配置项，则为升级场景写入 off（兼容历史调用）。
  - 若已存在配置项，则保留用户历史选择，不覆盖。

### 版本倾斜策略

- 本能力主要发生在入口层（oauth-proxy/filter）与服务自身，对控制面/节点版本倾斜不引入新的强约束；多集群代理能力与权限（clusters/proxy、services/proxy）维持原有兼容性要求。

## 缺点

- 引入额外鉴权链路与配置治理成本。
- 若规则维护不严谨，可能导致误拦截或长期遗留兼容规则无法收敛。

## 替代方案

使用 Kubernetes 原生 ClusterRole 的 nonResourceURLs 来描述业务 URL：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cluster-non-resource-access
rules:
- nonResourceURLs:
  - /readyz
  - /version
  - /metrics
  verbs: ["get"]
```

对比结论：
- ClusterRole nonResourceURLs 不支持复杂路径参数表达与按服务拆分治理；同时在聚合与跨服务维护方面不如 ConfigMap 策略灵活。
- 本提案采用 ConfigMap + SAR 的方式更贴合“服务自描述 + 平台统一执行”的落地路径。

## 所需基础设施（可选）

- 无新增仓库要求；需要在安装部署脚本中增加全局策略 ConfigMap 的创建与升级兼容逻辑。
