# openFuyao安全设计指南
本规范主要参考业界广泛标准和开源最佳实践，结合openFuyao业务发展趋势，制定出openFuyao开源安全设计指南，用于指导开发者进行模块设计，避免出现高安全设计风险。

## 1. 系统应用安全

**1.1** 所有能对系统进行管理的接口（包括人机接口、跨信任网络的机机接口），都需具备接入身份认证机制（标准协议定义中无认证机制的除外），相关接入身份认证机制应缺省启用。

**应对风险**：接入身份认证机制是识别用户身份的重要手段，若管理面无认证或认证机制缺省关闭，则任何人均能访问系统，易造成攻击者非法登录系统进行恶意操作等安全风险。

**1.2** 对于每一个需要授权访问的请求都需要核实用户身份、是否被授权执行这个操作。认证和授权访问的最终决策应在服务端完成。  
**应对风险**：将鉴权的处理过程放在客户端实现是不可靠的，恶意攻击者可以通过代理（如使用WebScarab）、篡改等方法轻易绕过。

**1.3**  Web应用程序的会话标识必须具备随机性；身份验证成功后，必须更换会话标识。
**应对风险**：如果web应用程序生成的会话标识不具备随机性，那么会话标识会存在被预测的风险。用户身份认证通过后，若不及时更换会话标识，会发生会话劫持。

**1.4** 系统对外部开放的接口、操作指令必须记录审计日志，记录包括用户ID、时间、事件类型、被访问资源的名称、访问发起端地址或标识、访问结果。查询类操作如果不涉及敏感信息，则不需要记录审计日志  
**应对风险**：日志内容要能支撑事后的审计，避免能改变系统行为的操作无法记录。

**1.5** 提供的日志（含运行日志和审计日志）模块/文件有相应的访问控制机制，禁止主动提供删除、修改审计日志的能力。  
**应对风险**：攻击者如果可以轻易获取日志信息或者调用接口删除、修改日志，则记录的日志就失去了问题追溯的意义。



## 2. 传输安全

**2.1** 在非信任网络之间进行敏感数据或关键业务数据传输，应支持安全传输协议或者加密后传输。  
**应对风险**：在跨网络进行传输时，容易遭受攻击者窃取或篡改，建议全程使用安全传输协议。

**2.2** 不应使用SSL2.0、SSL3.0、TLS1.0、TLS1.1协议进行安全传输，推荐使用更安全协议TLS1.2和TLS1.3。  
**应对风险**：早期的协议版本已经不再安全，SSL2.0和SSL3.0协议因存在很多安全问题已分别于2011年3月和2015年6月被IETF禁用。TLS1.0协议中对称加密算法仅支持RC4算法和分组加密算法的CBC模式，RC4已经公认不安全并被IETF在TLS所有版本协议中禁用，而对称算法的CBC模式存在IV可预测的问题，从而容易受到BEAST攻击。



## 3. 敏感&隐私数据保护

**3.1** 认证凭据(如口令、密钥等)应加密存储在系统中，应该加密保护，在不需要还原明文的场景，应使用不可逆PBKDF2算法加密。

**应对风险**：明文存储容易直接泄露口令信息。

**3.2** 对敏感数据的访问，根据风险采取适当的安全机制。  
**应对风险**：对于敏感数据不进行访问控制，低权限用户则容易获取归属于他人的敏感数据。

**3.3** 日志、调试信息、错误提示等信息中应过滤或者屏蔽明文凭据（口令/私钥/预共享密钥等）。  
**应对风险**：直接显示明文会被攻击者轻易获取，造成敏感信息泄露。

**3.4** 默认不应直接读取数据主体的个人数据，如果需要，则要提供相应接口获得数据主体授权。  
**应对风险**：个人数据都属于数据主体，如果需要访问和收集，需要获取数据主体同意并授权，否则会被判定为非法采集、传输个人数据。

**3.5** 默认不允许将个人数据、训练和推理的过程数据转移给第三方，如果需要，则要提供相应接口获得数据主体授权。  
**应对风险**：未提供合理方式告知数据主体转移的个人数据类型、转移目的以及数据接收方的相关信息，并获得数据主体的同意，会被判定为非法采集、传输个人数据

**3.6**  必须给数据主体提供撤销同意或退出个人数据收集的方式、渠道。数据主体撤销同意之后，禁止继续收集和使用相应的个人数据。  
**应对风险**：如果未提供数据主体撤销同意或退出数据收集的方式、渠道，监管机构将认为数据主体的同意不是“自由”给出，进而导致数据主体同意无效，数据收集处理缺乏合法依据。



## 4. 加密算法&密钥安全

**4.1** 系统中应该使用业界公开的、标准的密码学算法，和使用经过权威机构（如ISO、RFC等）推荐或认可的密码学算法库，禁止使用私有的、非标准密码算法实现加解密。  
**应对风险**：非密码学专业人员设计的密码算法，其安全强度难以保证。另一方面，这类算法在技术上也未经业界分析验证，有可能存在未知的缺陷，并且这样的设计违背公开透明的安全设计原则。

**4.2** 禁止使用不安全的密码算法，推荐使用强密码算法。  
**应对风险**：随着密码技术的发展以及计算能力的提升，一些密码算法已不再适合现今的安全领域，如果继续使用不安全的密码算法，可能导致机密信息泄露或者完整性破坏等结果。  
**已知的不安全密码算法**   
对称加密（分组加密）：Blowfish, DES, DESX, RC2, Skipjack, 2TDEA, TEA，3DES（加密传输协议TLS/SSH密码协议中必须禁止使用3DES，非密码协议场景必须保证密钥K1≠K2≠K3），CAST-128、IDEA  
对称加密（流加密）：SEAL, CYLINK_MEK, RC4  
哈希算法：SHA0, MD2, MD4, MD5, SHA1(数字签名、Hash-only场景),RIPEMD, RIPEMD-128  
非对称加密：RSA (小于 2048 bits)，ECIES (小于 224bits)，DLIES（小于2048bits)  
数字签名：RSA (小于2048 bits)，DSA (同X9.42标准DH，小于 2048 bits)，ECDSA(小于224bits)  
密钥协商（DH）：L<2048 bits，N*<224 bits  
密钥协商（ECDH）：ECDH(小于 224bits)  
MAC（消息验证码）算法：HMAC-MD5  
密码协议：SSH服务所有带CBC模式的算法，TLS中带CBC模式的算法（目前TLS 1.2中含CBC的套件没有已知的攻击，业界仍被使用，不在不安全算法内），匿名算法套件  


**4.3** 用于对数据进行加密的密钥不能在代码中硬编码。  
**应对风险**：密钥要支持替换，避免长期使用增加被泄露风险。

**4.4** 密码算法中使用到的随机数应是密码学意义上的安全随机数。  
**应对风险**：随机数用于生成IV、盐值、密钥等，都属于密码算法用途。不安全的随机数使得密钥、IV等可被全部或部分预测。

**4.5** 用于产生密钥的随机数发生器应使用安全随机数发生器。 例如可以使用： OpenSSL库的RAND_bytes、Linux操作系统的/dev/random设备接口、TPM中的随机数产生器（RNG）模块。
**应对风险**：使用不安全的随机数发生器来产生密钥，可能会使得到的密钥存在被预测的风险。



## 5.系统账号管理

**5.1**  系统未使用账号应默认禁用。
**应对风险**：如果不删除或禁用不使用的默认账号，攻击者获悉这些账号后，可能利用这些账号对系统或数据进行访问，导致信息泄露等风险。

**5.2**  所有账号的口令，需提供修改机制。
**应对风险**：如果系统存在账号的口令不支持修改，口令被攻击者获悉（如通过逆向分析或社会工程等手段）后，会使得系统中的认证机制形同虚设。

**5.3** 根据权限最小化原则，新建应用系统账号默认只给分配最小权限，运行软件程序的账号要尽可能使用操作系统低权限的账号。  
**应对风险**：防止程序本身出现漏洞时攻击者获得管理员的权限。

**5.4** 用户修改自身口令前，需验证旧口令，并且仅可以修改自身账号的口令。管理员重置其他用户的口令，无需验证旧口令  
**应对风险**：修改口令时不验证旧口令，无法验证用户身份，将可能导致合法用户口令被攻击者修改。

**5.5** 在输入错误的用户名或密码时，不能出现类似于“密码错误”、“用户名不存在”之类的过于明确的原因提示信息。  
**应对风险**：防止攻击者用于猜解系统用户名/口令。



## 6. 安全资料

6.1 系统使用到的默认用户/口令都必须在资料中说明，并提醒用户部署完系统后进行修改。  
**应对风险**：默认口令如果不修改，容易被攻击者用来访问系统内外部接口。

6.2 对外通信连接必须是系统运行和维护必需，系统开放的所有侦听端口（不含本地侦听端口127.0.0.1）需要在详细设计文档中说明，动态侦听端口必须限定合理范围。  
**应对风险**：若对外通信端口不在文档中说明，则可能会影响用户防火墙的放行规则的配置。  

6.3 系统中安全能力相关的功能，如果存在不安全的配置选项，需在资料中输出安全配置项清单。  
**应对风险**：若配置不当会导致安全风险，需提供清单支撑使用者做好安全配置。
