# AI辅助资料质检skill设计

## 概述

基于资料写作规范，总结清晰质检规则，生成doc-reviewer质检skill并归档到openFuyao/openfuyao-powers代码仓的skills文件夹下。该skill按公共基础规则与开源项目独有规则对文档进行结构化质检，涵盖标点符号、内容一致性、操作规范、描述精准度等维度，输出含分级问题与量化评分的 Markdown 评审报告，供相关开发者对在质检文档、审阅文档、检查文档规范性时使用。

## 质检规则

# 文档质检规则

## 规则分级

| 级别 | 含义 | 是否阻塞 |
|------|------|----------|
| **严重** | 违反必须遵守的规范，影响文档正确性、完整性或可用性 | 是 |
| **建议** | 违反推荐性规范，影响文档质量但不影响正确理解 | 否 |

## 规则适用范围

| 文档类型 | 适用规则 | 判定依据 |
|----------|----------|----------|
| **操作类** | 公共基础（全部）+ 开源项目独有（全部） | 含命令、步骤、安装/升级/配置等操作指导 |
| **设计类** | 公共基础（全部）+ 结构性 + 描述性 + 链接与格式（OS-21、OS-22） | 含架构设计、方案设计、接口设计等 |
| **描述类** | 公共基础（全部）+ 结构性 + 描述性 + 链接与格式（OS-21、OS-22） | 含产品说明、概念介绍、规格说明等 |
| **未分类** | 公共基础（全部）| 无法从内容判定类型时，仅执行公共基础规则 |

判定优先级：用户显式声明 > 从内容推断 > 未分类（仅公共基础）。

## 一、公共基础检查规则

适用于所有中文 Markdown 文档，无论文档类型。

### PF-01 标点符号使用正确

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：中文文档中是否错误使用了英文标点符号。中文文档中，以下标点应使用中文标点，不能用英文标点代替：

- 中文逗号【，】不能用英文逗号【,】代替
- 中文句号【。】不能用英文句号【.】代替
- 中文引号【""】不能用英文引号【""】代替（注意：英文直引号的 Unicode 是 U+0022（"），中文左引号是 U+201C（"），中文右引号是 U+201D（"）。只有出现 U+0022 才报告英文引号误用，U+201C 和 U+201D 是正确的中文引号绝不报告）
- 中文冒号【：】不能用英文冒号【:】代替
- 中文单引号【''】不能用英文单引号【''】代替
- 中文感叹号【！】不能用英文感叹号【!】代替
- 中文问号【？】不能用英文问号【?】代替

**不报告英文标点的情况**（以下场景英文标点属于正常用法）：

- **不检查的标点符号**：【>】【<】【/】【\】【|】【*】【#】【@】【&】【^】【~】这类中英文通用符号，禁止报告
- 标题当中的标点，如【Figure: 图一】【Note: XX】【Table: XX】
- 代码块（\`\`\`包裹）和行内代码（\`包裹）中的标点
- 数字列表序号，如【1.】【2.】【1)】【2)】
- 数学公式和计算表达式，如【N.QosFlow/N.Total*100%】
- 版本号和编号，如【v26.03】【v26.03-rc1】
- 术语或参数名称，如【25.1.2.SPC】【智能备电管理(LTE/NR/UMTS)(每小区)】
- 密码和密钥示例，如【Admin@1234】【~@#^*-_+[{}]:./?%=!】
- 单位符号，如【km/h】【bit/s】【dB】【°C】
- 超链接 URL，如【https://example.com】【x-wc://file=xxx.xml】
- 文件名和文件路径，如【config.xml】【/opt/data/file.txt】【C:\Windows\System32】
- 命令行指令和参数，如【ping -t 192.168.1.1】【grep -r "keyword" /path】
- 术语和组件名称中的标点，如【openFuyao-system-controller】【kube-apiserver】【E-RAB】
- 文档名称和书名中的标点，如【《通过前台(Web页面)删除业务集群》】
- 英文缩写和技术术语，如【AC】【DC】【IP】【CPU】
- 数学符号和特殊符号，如【≤】【≥】【±】【×】
- 表格中的连字符和范围符号，如【10-30】【A-Z】
- 浏览器地址栏内容
- Markdown 超链接，如【[https://gitcode.com/openFuyao/openfuyao-powers/blob/master/skills/doc-reviewer/SKILL.md](https://gitcode.com/openFuyao/openfuyao-powers/blob/master/skills/doc-reviewer/SKILL.md)】
- 换行符【\<br>】等 HTML 标签
- IP 地址，如【192.168.1.1】
- 带单位的数值范围，如【0.1~1000】
- 菜单路径中的【>】分隔符，如【系统管理 > 用户管理】
- 其他根据语义判断属于正确使用英文符号的情况

**判断原则**：判断时需考虑上下文，英文标点在英文或技术内容中属于正常用法。宁可漏报也不要误报，对于有歧义的情况不报告。

**正确示例**：
- 系统支持多种配置方式，具体操作请参见相关章节。→ 使用中文句号
- 执行命令：ping -t 192.168.1.1 → 命令行中的英文标点正常
- 下载文件 config.xml 后执行安装。→ 文件名中的英文标点正常
- 通过增量包补充 openFuyao-system-controller 及其依赖镜像和 Chart。→ 产品/组件名称中的连字符正常

**错误示例**：
- 系统支持以下功能,请根据需要选择. → 错误使用了英文逗号和句号
- 系统提示"操作成功"后继续 → 错误使用了英文引号代替中文引号

### PF-02 标点符号成对

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word |

**检查内容**：括号和引号必须成对出现且方向正确：

- 中文括号【（）】必须成对，不能只有左括号或只有右括号
- 中文方括号【【】】必须成对
- 中文双引号【""】必须成对，且左引号【"】必须在右引号【"】之前
- 中文单引号【''】必须成对，且左引号【'】必须在右引号【'】之前

**不报告配对问题的情况**：
- 括号或引号在代码块（\`\`\`包裹）或行内代码（\`包裹）中
- 数字列表序号如【1)】【2)】中的括号
- 英文括号【()】【[]】在英文术语、公式、代码中属正常用法，不检查其配对
- 书名号【《》】中包含的括号不计入配对统计
- 密码和密钥示例，如【~@#^*-_+([{}]:./?%=!】
- 参数取值说明，如【角色名称长度小于或等于64个字符，且不能包含\`~*(|[]{}:,+;="'<>/?\特殊字符】

**正确示例**：
- （注意：此操作不可逆。）→ 中文括号成对使用，正确

**错误示例**：
- 配置完成（保存设置后生效。→ 中文括号未成对，缺少右括号
- "系统配置"说明如下 → 引号顺序错误，右引号在左引号之前

### PF-03 空白元素

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word |

**检查内容**：是否存在以下空白元素：

- 空章节
- 空表格
- 表格空白行
- 表格空白格
- 无内容列表项
- 无内容 section
- 图有标题无图片
- 说明/注意/须知无内容
- 空锚点（Markdown 链接 `[]()` 链接文本为空；HTML 锚点 `<a name="xxx"></a>` 无实际内容）

空白元素是指该元素内容为空，只要有内容则本条规则不报错，不用分析具体内容是否相关。

**例外**：写作模板类文档无需检查是否有空白元素。

**写作模板类文档判定标准**（满足任一即可）：
- 文档 frontmatter 或标题中明确含"模板""template"字样
- 文档内容以占位符（如 `<xxx>`、`【待填充】`、`TODO`、`<!-- 填写 -->`）为主体，实际内容尚未填充
- 用户显式声明为模板

无法判定时，默认执行空白元素检查（即不适用例外）。

**错误示例**：
- `| 列1 | 列2 | 列3 |\n| value1 || value2 |` → 存在表格空白格
- `1. XXX\n2.\n3. XXX` → 存在无内容列表项

### PF-04 连续重复字词

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word |

**检查内容**：是否存在因手误导致的连续重复字或词（即同一个字或词紧挨着出现两次）。

**判断标准**：只报告紧挨着连续出现的重复，如"的的"、"进行进行"。

**不报告的情况**：
- 同一个字在句子不同位置出现多次，如"的确如此，的确"
- 同一句话在文档中出现多次
- 有意重复的表达，如"慢慢"、"仔细仔细"
- 表格中合并单元格拆分导致的相邻单元格内容一样，如 `| 系统规格 | 系统规格 | 系统规格 |`
- 行内包含 `|` 分隔符的内容说明是表格行，相邻单元格内容相同属于合并单元格拆分，不报告
- NOTE、WARNING 等提示块出现在表格行中被 `|` 分隔重复，不报告

**正确示例**：
- 系统会自动重启，重启后生效 → "重启"不是紧挨重复
- 请仔细检查，仔细确认 → 不是紧挨重复
- `| NOTE: 内容说明 | NOTE: 内容说明 | NOTE: 内容说明 |` → 表格合并单元格拆分，不是重复错误

**错误示例**：
- 系统进行进行配置 → "进行"紧挨重复
- 操作的的方法 → "的"紧挨重复

### PF-05 内容前后一致

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word |

**检查内容**：对于同一对象的描述是否前后一致。具体检查以下子项：

1. **术语名称一致**：同一概念/组件/参数/模块在不同章节的名称是否一致。例如前文称"管理面"，后文不应改称"控制台"或"管理界面"（除非首次出现时已注明别名）
2. **数值一致**：同一配置项/规格/版本号/端口号等在前后文中是否一致。例如前文写"默认端口 8080"，后文不应写"默认端口 8443"
3. **步骤描述一致**：同一操作在不同位置的描述是否一致。例如前文步骤写"单击保存"，后文引用时不应写"点击确认"
4. **图示与文字一致**：图中的标注、流程、层级等是否与正文文字描述一致。例如图中标注 3 个节点，正文不应写"5 个节点"
5. **状态/结论一致**：前文得出的结论或状态在后续章节不应与之矛盾。例如前文说"支持热升级"，后文不应写"升级前需停止服务"

### PF-06 语言表达正确

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：是否存在严重影响读者理解的复杂语句或长语句。

**判断标准**（需同时满足以下条件才报告）：
- 句子存在非常明显的语义混乱、逻辑跳跃或表意不清
- 读者需要反复阅读才能理解句子含义
- 不能仅凭句子长度判断，长句子如果逻辑清晰、语义连贯则不报告
- 不能仅因为"可以拆分得更简洁"或"建议优化可读性"而报告

**不报告的情况**：
- 句子虽长但结构清晰，各分句之间逻辑关系明确
- 句子包含列举内容（如"根据 A、B、C 进行分析"）
- 技术文档中的专业描述，即使较长也属正常
- 句子包含多个独立的简单陈述，即使句子较长，但每个分句本身表意清晰
- 任何能够正常阅读理解、只是"可以更精简"的句子

**严格程度**：只报告读者无法正确理解原意的极端情况，不要因为内容可以更好就报告问题，宁可漏报也不要误报。

**正确示例**：
- 根据工程参数、性能数据、配置数据等输入信息，对网络 KPI 进行分析，生成并下发节能优化建议 → 虽然较长但结构清晰，逻辑连贯，表达正确

**错误示例**：
- 在完成对系统的基本配置并确认所有相关参数均已按照实际业务需求进行了正确设置之后还需要同时兼顾到其他模块的配置情况 → 多个从句嵌套，逻辑关系不清

### PF-07 IP 合法

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word |

**检查内容**：文档中不能出现公网 IP 地址，当出现 IP 地址时，必须属于私网范围。

**IPv4 地址**：必须属于以下私网段之一：
- A 类：10.0.0.0 - 10.255.255.255
- B 类：172.16.0.0 - 172.31.255.255
- C 类：192.168.0.0 - 192.168.255.255

**版本号与 IP 地址的区分标准**：

满足以下任一条件时，四段数字**不作为 IP 地址**检查：
1. **以 v 开头或含字母后缀**：如 `v20.0.1.2`、`v26.03-rc1`
2. **出现在版本/发布语境中**：前后文含"版本""version""release""升级""update"等词，如"版本 20.0.1.2"
3. **第一段为 0**：IPv4 第一段不为 0，版本号可含 0，如 `0.9.1.2`
4. **任意一段超过 255**：如 `26.3.0.1000`
5. **用户显式声明为版本号**：用户在对话中说明某格式为版本号而非 IP

不满足以上条件的四段数字（如 `8.8.8.8`、`114.114.114.114`）视为 IP 地址，按私网范围检查。

**IPv6 地址**：必须属于以下私网段之一：
- fc00::/7（ULA 唯一本地地址）
- fe80::/10（链路本地地址）

### PF-08 句子结尾标点

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：完整句子必须以句号（。）结尾。

**例外情况**：
- 标题
- 短语
- 列表中的名词性短语
- 表格行
- 代码块
- 图片行
- 链接

以上内容可以不以句号结尾。

**正确示例**：
- `Table: 版本信息` → 表格标题，可以不以句号结尾
- `1. 登录系统\n2. 进入用户管理页面\n3. 单击新建用户` → 列表中的名词性短语，可以不以句号结尾

**错误示例**：
- `请按照如图所示操作指导注册账户` → 完整句子，未以句号结尾

### PF-09 单位书写规范

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：文档中涉及的 Kubernetes、电学术语、物理单位和词头须符合以下规范：

1. **AC/DC/RMS 全大写**：交流/直流/均方根缩写必须全大写，写作 AC、DC、RMS，不能写作 ac、Ac、dc、Dc、rms、Rms 等大小写混合或小写形式
2. **组合单位中英文不混用**：组合单位（含 / 或 · 连接）中不能同时混用中文单位名称和 SI 符号。例如 km/小时 应改为 km/h
3. **词头不得孤立使用**：词头（K、M、G、T、k、μ、n、p）不能单独跟在数字后使用，必须与单位符号连用。例如 64K 应改为 64Kbit/s
4. **数值+单位与缩略语之间需空格**：数值和单位符号后面紧跟 AC、DC、RMS、RH 等缩略语时，单位与缩略语之间必须保留空格。例如 220VAC 应改为 220V AC

### PF-10 枚举完整性

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word |

**检查内容**：正文声明了具体数量的枚举，但实际列举项数量与声明不一致。

**判断标准**：
- 正文中出现"分为以下 N 种/类/项/个""包含 N 个方面""N 个步骤"等明确的数量声明
- 实际列举的项数与声明的数量 N 不符

**不报告的情况**：
- 使用"等""例如""如"等不定数量词（如"包括 A、B 等"），不要求精确计数
- 使用"以下"但未给出具体数量（如"分为以下几种"），不检查项数
- 列举项因排版跨段、跨列表难以计数时，不报告

**正确示例**：
- "系统支持三种认证方式：A、B 和 C。" → 声明 3 个，实际 3 个
- "包括 A、B 等。" → 使用"等"，不检查项数

**错误示例**：
- "系统支持三种认证方式：A 和 B。" → 声明 3 个，实际 2 个
- "配置分为以下四个步骤：1. ... 2. ... 3. ..." → 声明 4 步，实际 3 步

### PF-11 因果/推导关系

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：使用"因此""所以""由于""导致""由此可见"等因果关联词时，后面的结论是否能从前文条件合理推导得出。

**判断标准**（需同时满足才报告）：
- 文档中使用了明确的因果关联词
- 结论与前文所述条件之间存在明显的逻辑断裂或矛盾

**不报告的情况**：
- 因果关系虽不严密但方向大致正确（如省略了部分中间推导步骤）
- 属于经验性/工程性判断，无法严格逻辑推导但属行业共识
- 宁可漏报也不要误报，对于有争议的因果关系不报告

**正确示例**：
- "由于 Pod 的 CPU 限制设置为 100m，因此当负载超过 0.1 核时会出现节流。" → 因果关系成立

**错误示例**：
- "由于系统使用 Kubernetes，所以不支持热升级。" → 因果关系不成立（Kubernetes 本身不排斥热升级）

### PF-12 步骤时序逻辑

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word（操作类文档） |

**检查内容**：操作步骤的先后顺序是否合理，是否存在依赖倒置或逻辑矛盾。

**判断标准**：
- 后续步骤依赖前置步骤的产物（如配置文件、安装结果），但前置步骤未先执行
- 步骤中要求"先验证再配置"但实际顺序写反
- 步骤中引用了尚未创建的资源/对象

**不报告的情况**：
- 可并行执行的步骤，顺序不固定
- 步骤虽可优化但当前顺序不构成错误
- 设计类/描述类文档中的非操作流程性内容

**正确示例**：
- "1. 安装组件 A 2. 配置组件 A 3. 启动组件 A" → 安装→配置→启动，顺序合理

**错误示例**：
- "1. 启动组件 A 2. 安装组件 A 3. 配置组件 A" → 启动在安装之前，顺序错误
- "1. 编辑 config.yaml 2. 创建 config.yaml 文件" → 编辑了尚未创建的文件

### PF-13 条件-结论匹配

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word |

**检查内容**：前提条件与正文得出的结论是否矛盾。

**判断标准**：
- 前提条件声明了某状态/环境，但正文结论要求的前提与之冲突
- 前提说"已安装 A"，但步骤中又要求"先安装 A"
- 前提说"集群已运行"，但结论说"完成安装后集群开始运行"

**不报告的情况**：
- 前提条件分多个场景（如"场景一：已安装；场景二：未安装"），不同场景下结论不同
- 前提条件有补充说明，整体不构成矛盾

**正确示例**：
- 前提："已安装 openFuyao" → 步骤："升级 openFuyao" → 合理（已安装才能升级）

**错误示例**：
- 前提："已安装 openFuyao" → 步骤："安装 openFuyao" → 矛盾（已安装为何再安装）
- 前提："集群处于运行状态" → 结论："安装完成后，集群将进入运行状态" → 矛盾（前提已运行，结论说将要运行）

### PF-15 主谓搭配/成分残缺

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：句子是否存在主谓搭配不当或成分残缺，影响理解。

**检查子项**：
1. **主语缺失**：长句中主语被省略，导致无法判断动作执行者
2. **主谓不一致**：主语与谓语在单复数或语义上不搭配
3. **宾语残缺**：及物动词后缺少宾语，句子不完整
4. **定语/状语悬空**：修饰语找不到被修饰对象

**不报告的情况**：
- 操作步骤中的祈使句（省略主语"你"属正常用法），如"单击保存"
- 技术文档中常见的被动句式省略主语
- 句子虽可补充成分但不影响理解
- 宁可漏报也不要误报

**正确示例**：
- "单击保存按钮。" → 祈使句省略主语，正常
- "系统自动检测并修复异常。" → 主谓搭配正确

**错误示例**：
- "通过配置参数后，可以提升性能。" → 主语缺失（谁提升？）
- "该功能主要解决和优化。" → 宾语残缺（解决什么？优化什么？）

### PF-16 指代不明

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：代词（"它""其""该""此""这些"等）出现时，前文是否存在多个候选指代对象，导致指代歧义。

**判断标准**（需同时满足才报告）：
- 使用了代词或指代词
- 前文最近语境中存在 2 个及以上可能的指代对象
- 无法明确判断代词指向哪一个

**不报告的情况**：
- 前文只有一个候选对象，指代明确
- 代词紧接被指代对象（如"Kubernetes。它支持..."），无歧义
- 技术文档中"该组件""此功能"等在上下文清晰时不报告
- 宁可漏报也不要误报

**正确示例**：
- "安装 openFuyao 后，启动它。" → 前文只有 openFuyao，指代明确

**错误示例**：
- "安装组件 A 和组件 B 后，启动它。" → "它"指向 A 还是 B？
- "配置文件和密钥已生成，将其复制到 /etc 目录。" → "其"指向配置文件还是密钥？

### PF-17 数字使用规范

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：中文数字与阿拉伯数字的使用是否规范。

**判断标准**：
- **应用阿拉伯数字的场景**：版本号、端口号、规格数值、百分比、时间、日期、度量值、IP 地址
- **应用中文数字的场景**：成语/惯用语（如"一对一""三要素"）、概数（如"七八个"）、非计量的大数（如"万级"）
- **一致性**：同一文档内同类场景的数字风格应统一

**不报告的情况**：
- 约定俗成的表达（如"零配置""百兆"）
- 编号/序号（如"步骤 1"与"步骤一"均可）
- 代码块、命令行中的数字
- 宁可漏报也不要误报

**正确示例**：
- "系统支持 3 个节点" → 计量用阿拉伯数字
- "支持一对一映射" → 成语用中文数字
- "版本 v26.6.0" → 版本号用阿拉伯数字

**错误示例**：
- "系统支持三个节点，每个节点配置 8 核 CPU" → 计量数字混用风格（同类场景应统一）

### PF-18 图文内容对应

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | md, word |

**检查内容**：图片的说明文字、标注内容与正文描述是否对应。

**检查子项**：
1. **图标题与正文引用一致**：正文引用图时所说的内容与图标题/说明一致
2. **图中标注与文字一致**：图中标注的名称、数值、流程方向等与正文描述一致
3. **图存在但有 alt 文本缺失**：Markdown 图片 `![]()` 中 alt 文本为空
4. **正文引用了不存在的图**：正文写"如下图所示"但该位置无图片

**不报告的情况**：
- 图片为装饰性插图，无对应文字描述
- alt 文本虽简短但已描述图片内容

**正确示例**：
- 正文："系统架构如下图所示。" + 图标题："图1：系统架构图" → 对应一致

**错误示例**：
- 正文："如图2所示，系统包含3个模块" + 图2实际显示5个模块 → 图文不一致
- 正文："如下图所示" + 该位置无图片 → 引用了不存在的图
- `![](architecture.png)` → alt 文本为空

### PF-19 标题层级规范

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md |

**检查内容**：Markdown 标题层级是否符合规范。

**检查子项**：
1. **H1 唯一**：一篇文档应只有一个 H1（`#`）标题
2. **层级不跳级**：不应从 H1 直接跳到 H3（如 `#` 后紧跟 `###`），应逐级递进
3. **标题不重复**：同一层级下不应出现标题文本完全相同的标题
4. **标题不以标点结尾**：标题末尾不应有句号、逗号等标点

**不报告的情况**：
- 代码块中的 `#` 注释
- Markdown frontmatter 中的 `#` 键
- 有意为之的特殊文档结构（如 changelog）

**正确示例**：
```markdown
# 文档标题
## 一级章节
### 二级小节
```

**错误示例**：
```markdown
# 文档标题
### 跳级小节    ← H1 直接跳到 H3
```
```markdown
# 概述
## 概述         ← 同级标题重复
```

### PF-20 图标题统一

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md |

**检查内容**：文档中所有图片必须配有图标题，图标题格式为 `图N：标题描述`（N 为全文图片的顺序编号）。

**检查子项**：
1. **有图无标题**：图片存在但缺少图标题（alt 文本为空或仅写"输入图片说明""图片"等占位文字，且图片上下方无 `图N：xxx` 形式的标题行）
2. **图编号不连续**：图编号应从 1 开始递增，不跳号、不重复
3. **图标题缺失描述**：图标题仅写"图1""图2"等编号，无实际描述内容

**不报告的情况**：
- 提示性图标（如 `icon-note.gif`、`icon-warning.gif` 等装饰性图标），不作为内容图片检查
- 代码块中的图片语法
- 用户显式声明无需图标题的文档

**正确示例**：
```markdown
![系统架构图](figures/architecture.png)

**图1：系统架构图**
```

**错误示例**：
- `![](architecture.png)` → 无 alt 文本，无图标题
- `![输入图片说明](architecture.png)` → alt 文本为占位文字，无实际图标题

### PF-21 中英文混合不加空格

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md, word |

**检查内容**：中文字符与英文字母、数字之间不添加空格。

**判断标准**：
- 中文字符与英文字母相邻时，中间不应有空格
- 中文字符与数字相邻时，中间不应有空格

**正确示例**：
- `openFuyao系统支持多种部署模式。` → 中英文之间无空格
- `系统支持3个节点` → 中文与数字之间无空格

**错误示例**：
- `openFuyao 系统支持多种部署模式。` → 中英文之间多了空格
- `系统支持 3 个节点` → 中文与数字之间多了空格

**不报告的情况**：
- 代码块和行内代码中的内容
- 英文句子内部的空格
- 表格中的内容
- Markdown 语法元素
- 超链接和 URL 中的空格
- frontmatter 中的内容
- 中英文之间有标点符号分隔的情况

### PF-22 章节标题规范

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | md |

**检查内容**：章节标题中不使用特殊符号，且不轻易添加数字编号。

**检查子项**：

1. **禁止在标题中使用特殊符号**：数学符号（±、×、÷、≥、≤等）、技术符号（->、=>、||、&&等）、装饰符号（★、☆、◆等）、Emoji 表情符号、连续特殊字符组合

2. **标题数字编号审视**：标题中不轻易添加数字编号（如 `1`、`1.1`、`1.1.1`、`一`、`二` 等序号前缀）。资料会在统一网站上呈现，部分文档标题加了数字编号而部分未加，会导致导航栏中标题样式不一致。发现时上报为建议问题，提示人工审视该数字编号是否必要。

**允许在标题中使用的内容**：
- 中英文文字
- 数字（用于版本号、端口号等语义性数字，如 `v26.06 升级指南`，非编号用途）
- 中文冒号、问号等必要标点
- 连字符、斜杠、小括号

**不报告的情况**：
- 代码块中的 `#` 注释
- Markdown frontmatter 中的 `#` 键
- 有意为之的特殊文档结构（如 changelog、修订记录）
- Markdown 有序列表项不作为标题检查

**错误示例**：
```markdown
## 集群安装 ★必读★
## 1 安装
### 1.1 环境准备
## 一、安装概述
```

### 2.5 链接与格式规范

#### OS-21 参考内容链接规范

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | 操作类、设计类、描述类 |

**检查内容**：文档中所有参考、引用内容必须使用超链接或相对链接形式，且链接目标必须指向仓库公共有效分支，禁止链接到个人分支。

**检查子项**：
1. **参考内容必须使用链接**：涉及"参见""参考""详见"等引用语义时，必须使用可点击的超链接（`[文字](URL)`）或相对链接（`[文字](相对路径)`），不能仅写纯文字描述
2. **链接目标分支校验**：URL 中包含分支路径的链接，分支名必须是仓库公共有效分支：
   - 允许的分支：`master`、`main`、版本分支（如 `26.09`、`v26.06`、`release-26.09` 等）
   - 禁止的分支：个人分支（如 `zhangsan/feature-x`）、临时分支、feature 分支
3. **相对链接路径有效**：相对链接指向的文件路径在当前文档所在仓库中应存在

**不报告的情况**：
- 外部站点链接（如 `https://kubernetes.io`）不检查分支
- 引用同一文档内的锚点（如 `[配置说明](#配置说明)`）不检查分支
- 代码块中的 URL

**错误示例**：
- `请参见集群安装指南章节。` → 纯文字描述，无链接
- `[升级指南](https://gitcode.com/openFuyao/sig-installation/blob/zhangsan/dev/docs/zh/upgrade_guide.md)` → 链接到个人分支

#### OS-22 说明/注意统一图标格式

| 属性 | 值 |
|------|-----|
| 级别 | 建议 |
| 适用 | 操作类、设计类、描述类 |

**检查内容**：文档中的说明、注意、警告等提示性内容必须统一使用带图标的 blockquote 格式。

**标准格式**：

````markdown
> ![输入图片说明](figures/icon-note.gif) **说明：**<br />内容...

> ![输入图片说明](figures/icon-warning.gif) **警告：**<br />内容...
````

**格式要求**：
1. 必须使用 blockquote（`> `）包裹
2. 必须包含图标图片：说明类使用 `icon-note.gif`，警告类使用 `icon-warning.gif`
3. 图标 alt 文本统一为 `输入图片说明`
4. 提示词必须加粗：`**说明：**`、`**警告：**`
5. 提示词后使用 `<br />` 换行
6. 图标路径使用相对路径指向文档仓库的 `figures/` 目录

**允许的提示类型与图标**：

| 提示类型 | 图标文件 | 加粗标签 |
|----------|----------|----------|
| 说明 | `icon-note.gif` | `**说明：**` |
| 警告 | `icon-warning.gif` | `**警告：**` |

**错误示例**：
- `**说明**：本操作需在root用户下执行。` → 未使用 blockquote 和图标
- `> 注意：此操作不可逆。` → 使用了 blockquote 但缺少图标

#### OS-23 操作步骤有序列表不合并

| 属性 | 值 |
|------|-----|
| 级别 | 严重 |
| 适用 | 操作类 |

**检查内容**：操作步骤必须使用有序列表（`1.`、`2.`、`3.`）逐步排列，每个步骤只包含一个独立操作，不得将多个操作合并为一个步骤。

**检查子项**：
1. **必须使用有序列表**：操作步骤必须使用 Markdown 有序列表，不能使用无序列表或纯段落文本描述步骤
2. **一步一操作**：每个步骤只描述一个独立操作动作，不得在一个步骤中合并多个独立操作
3. **不合并多命令**：多个独立命令应分步骤展示（有关联性的链式命令除外，如 `tar -xzf && cd` 可作为一个步骤）

**不报告的情况**：
- 步骤中包含必要的子步骤（嵌套有序列表）
- 有强依赖关系的链式命令可作为一个步骤
- 非操作流程性内容
- 配置说明中的多行配置项

**正确示例**：

````markdown
1. 使用root用户登录引导节点。
2. 将安装包上传至`/root`目录。
3. 执行以下命令解压安装包：
   ```bash
   tar -xzf bke-linux-amd64.tar.gz
   ```
4. 执行以下命令安装：
   ```bash
   sudo mv bke /usr/local/bin/
   ```
````

**错误示例**：

````markdown
- 使用root用户登录引导节点，上传安装包到/root目录，然后解压并安装。
````

## 三、源码一致性检查（可选）

### 触发机制

源码一致性检查为可选步骤。skill启动后读取文档、在文档类型判定前主动向用户询问：

> 本次文档内容是否涉及与代码实现的一致性检查？
>
> 如涉及，请提供源码文件/目录路径，将核对文档中的命令、配置、路径、功能描述与代码实现是否一致，不一致项将在报告中上报。如不涉及，可跳过此步骤。

- 用户提供源码路径 → 启用源码一致性检查
- 用户明确表示不涉及/跳过 → 跳过
- 用户未回复或回复模糊 → 跳过

### 检查流程

核心流程为「提取文档声明 → 在源码中定位对应实现 → 逐项比对并记录不一致」。

### 检查维度

#### 3.1 命令一致性

**文档侧提取**：扫描代码块和行内代码中的命令调用，提取命令名、子命令、flag/option列表。

**源码侧定位**：搜索CLI flag注册点（Go cobra/pflag、Python argparse/click、Shell getopts等），确认flag名、类型、默认值。

**比对要点**：
- flag名是否完全一致（含 `--`/`-` 前缀）
- 默认值是否一致
- 子命令是否全部注册
- 源码有但文档未提及的flag不上报（内部flag不报）

#### 3.2 配置一致性

**文档侧提取**：扫描YAML/JSON配置示例块、字段说明表格、正文中的默认值声明，提取配置项名称、默认值、取值范围。

**源码侧定位**：搜索配置结构体定义（struct tag、json/yaml tag）、默认常量、取值校验逻辑、CRD定义。

**比对要点**：
- 配置项名称与源码字段名/yaml tag是否一致
- 默认值是否一致
- 取值范围与校验逻辑是否一致

#### 3.3 路径一致性

**文档侧提取**：扫描正文和代码块中的绝对路径、目录结构描述，提取路径清单及用途。

**源码侧定位**：Glob枚举实际目录树，Grep搜索路径字符串常量。

**比对要点**：
- 目录是否存在且路径正确
- 文件名是否一致
- 路径用途是否一致

#### 3.4 功能描述一致性

**文档侧提取**：扫描正文中的功能陈述句，提取能力声明（"支持X"）、行为声明（"自动重试N次"）、约束声明（"最大N个节点"）、流程声明（"A后执行B"）。

**源码侧定位**：Grep搜索功能关键词，Read打开实现文件确认逻辑和参数。

**比对要点**：
- 文档声明"支持X"，源码中是否有对应实现
- 重试次数、上限值等约束是否匹配
- 执行顺序与流程编排是否一致

#### 3.5 版本号一致性

**文档侧提取**：扫描正文中的版本声明、代码块中镜像tag/CRD apiVersion/Chart version、表格中版本列，提取组件版本、镜像tag、API版本、依赖版本。

**源码侧定位**：搜索版本常量（`Version =`）、镜像tag（`image:`/`tag`）、CRD apiVersion/GroupVersion、依赖文件（`go.mod`/`Chart.yaml`）、版本校验逻辑。

**比对要点**：
- 文档声明的组件版本与源码版本常量是否一致
- 文档示例中的镜像tag与源码/Chart中实际tag是否一致
- 文档声明的CRD apiVersion与源码GroupVersion定义是否一致
- 文档声明的依赖版本与源码版本校验逻辑是否一致
- 同一文档中不同位置对同一组件的版本声明是否矛盾（如正文写v26.06但代码块写v26.09）

### 比对规则

1. **精确匹配优先**：命令名、flag名、配置项名、路径字符串、版本号采用精确匹配
2. **语义匹配补充**：功能描述采用语义比对
3. **只上报文档与源码的不一致**：源码中有但文档未提及的功能/flag/配置项不上报
4. **文档写了但源码中没有的，上报**：文档声明了命令/配置/功能，但源码中找不到对应实现

### 不一致等级与扣分

所有不一致项统一记为**严重**（与质检规则分级体系一致），扣分规则同公共基础（−10/个）。发现不一致后需重新计算量化评分。

### 报告输出

检查结果在质检报告中单列「源码一致性」章节，每条不一致项包含：检查类型、文档位置、文档声明、源码位置、源码实现、不一致描述、修复建议。

### 常见不一致模式

| 模式 | 示例 |
|------|------|
| flag名称不一致 | 文档写 `--enable-ssl`，源码注册为 `--tls-enable` |
| 默认值不一致 | 文档写"默认端口 8080"，源码常量为 `DefaultPort = 8443` |
| 路径不一致 | 文档写 `/etc/openFuyao/certs/`，源码实际路径为 `/etc/openFuyao/tls/` |
| 功能不存在 | 文档写"支持热升级"，源码中无升级相关reconcile逻辑 |
| 约束值不一致 | 文档写"最大 500 节点"，源码校验为 `if nodeCount > 200` |
| 版本号不一致 | 文档写组件版本 v26.06，源码常量为 `Version = "v26.09"` |
| 镜像tag不一致 | 文档示例写 `bke-controller:v26.06`，Chart values中实际tag为 `v26.09` |
| 文档内版本矛盾 | 正文写"适用于v26.06"，代码块中镜像tag写v26.09 |
