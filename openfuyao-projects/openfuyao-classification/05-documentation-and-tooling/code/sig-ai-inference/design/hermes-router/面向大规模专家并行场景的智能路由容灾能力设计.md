## 面向大规模专家并行方案的网关+智能路由容灾设计——以MindIE Motor为例
### 概括
#### 动机
昇腾MindIE Motor基于大规模专家并行（大EP）方案与某企业开展合作，大EP方案包含用于处理EP服务故障的`RAS`健康监测模块，但未提供网关服务来保障用户不受EP服务故障的影响。现希望在方案中引入智能路由hermes-router，基于`RAS`健康监测机制在网关层面做到推理请求自动切流、故障恢复以及负载均衡能力。
#### 目标
构建高可用的网关+智能路由容灾能力，实现以下核心能力：
1. **动态切流**：在EP服务故障或重启时，保证流量的无损或低损切换，并对失败请求进行重试。
2. **负载均衡**：在多个EP服务间均衡地分发请求。

#### 故事1：智能路由发现EP服务
##### 故事描述
大EP架构中每个EP集群都由一个Coordinator Pod作为代理对外提供推理服务，EP服务的coordinator需要进行相应配置，以支持智能路由动态发现服务和判断后端状态。
##### 故事流程
1. Coordinator Pod配置Label信息
2. Coordinator Pod配置健康探针以表明自身推理服务的可用状态
3. 智能路由的服务发现机制定期查询集群pod，基于Label信息发现EP服务后端
4. 智能路由对EP服务后端pod调用健康探针，若服务正常则加入可用服务列表
#### 故事2：智能路由自动切流
##### 故事描述
某大EP服务E不可用时，RAS将其杀死，智能路由能够及时感知该变化，将E从可用服务列表中删除；当RAS将E重新拉起后，智能路由判断E是否可用，待E可正常使用后将其加入可用服务列表。
##### 故事流程
1. RAS发现某大EP服务E不可用并将其杀死
2. 智能路由的可用服务列表更新，不再包含E，后续请求不再路由到E
3. RAS将E重新拉起
4. 智能路由发现新增EP服务E
5. 通过E健康探针判断E是否可用
6. 若E推理服务已就绪，智能路由将其加入可用服务列表，后续请求会路由到E

#### 故事3：网关请求重试
##### 故事描述
网关在某请求R超时或者失败后重新发送。
##### 故事流程
前提：已网关中配置重试规则
1. 请求R未能正确从EP服务后端获取返回内容，判断为请求失败
2. 网关对失败请求进行重试
3. 网关在规定重试次数内成功则返回正常结果，若未成功则返回失败结果

#### 故事4：智能路由实现推理请求的负载均衡
##### 故事描述
系统正常运行时，智能路由能应用路由策略实现请求的负载均衡。
##### 故事流程
前提：智能路由已在EPP中配置负载均衡相关的路由策略
1. 网关接受请求R，将R转发至EPP
2. EPP根据路由策略以及请求R的信息给出合适的EP后端
3. 网关将请求R转发至目标EP后端

#### 服务发现与健康检测
##### 服务发现机制

服务发现机制是智能路由的核心能力，用于动态发现和管理可用的后端服务Pod，实现自动化的后端服务管理。当新的后端服务Pod启动时，服务发现机制能够自动将其加入可用后端列表；当Pod下线或故障时，能够自动从列表中移除，确保路由系统始终使用最新的可用服务列表。

本方案通过InferencePool的`selector.matchLabels`机制来实现服务发现。InferencePool是Gateway API Inference Extension中定义的Kubernetes自定义资源，用于将一组专门用于服务AI模型的Pods组织成一个逻辑池。通过配置InferencePool的标签选择器，可以自动发现匹配标签的后端服务Pod，并维护其可用性状态。

要启用自动服务发现机制，需要完成以下配置：

创建InferencePool资源，配置`selector.matchLabels`来匹配后端服务Pod的标签。以下是配置示例：

```yaml
apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferencePool
metadata:
  name: inference-pool
spec:
  # 配置Pod选择器，匹配后端服务Pod的标签
  selector:
    matchLabels:
      app: inference-service
      role: serving
  # 指定Pod暴露的目标端口
  targetPorts:
    - number: 8000
  # 关联EPP Server，用于智能路由决策
  extensionRef:
    name: epp
    portNumber: 9002
```

关键配置说明：
- `selector.matchLabels`：定义用于匹配后端服务Pod的标签选择器。只有标签匹配的Pod才会被InferencePool发现和管理。
- `targetPorts`：指定Pod暴露的服务端口，InferencePool会将请求转发到此端口。
- `extensionRef`：关联EPP Server，指定EPP Server的名称和端口，用于获取智能路由决策。

为后端服务Pod的Deployment或Pod添加与InferencePool的`selector.matchLabels`匹配的标签。例如：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inference-service
spec:
  template:
    metadata:
      labels:
        app: inference-service      # 必须与InferencePool的selector.matchLabels匹配
        role: serving          # 必须与InferencePool的selector.matchLabels匹配
    spec:
      containers:
      - name: inference-service
        image: <inference-service-image>
        ports:
        - containerPort: 8000  # 必须与InferencePool的targetPorts一致
        # ... 其他配置
```

配置完成后，服务发现机制会自动工作，无需额外操作：

1. 自动发现流程：
   - InferencePoolController持续监听集群中匹配`selector.matchLabels`的Pod
   - 当新的后端服务Pod启动并打上匹配的Label后，Controller自动将其加入可用后端列表
   - EPP Server通过InferencePool获取最新的后端列表，用于路由决策

2. 动态更新机制：
   - Pod上线：当新的后端服务Pod启动并打上匹配标签后，InferencePool会自动将其加入可用列表，流量开始进入
   - Pod下线：当Pod被删除或标签不匹配时，InferencePool会自动将其从列表中移除，新流量不再路由到该Pod
   - Pod状态变化：根据K8s健康检查结果（readinessProbe/livenessProbe），自动更新Pod的可用性状态

3. Endpoint维护：
   - InferencePool维护的Endpoint指向Pod IP
   - 这些Endpoint会随着Pod的增删自动更新，无需手动干预
   - 网关通过InferencePool获取最新的Endpoint列表进行请求转发

##### 健康检测机制

健康检测机制是智能路由系统的重要组成部分，用于实时监控后端服务Pod的健康状态，确保只有健康的Pod才会接收流量。当Pod出现故障或不可用时，健康检测机制能够及时发现问题并触发相应的处理流程，实现自动的故障隔离和流量切换。

本方案采用业务监控 + 基础设施监控双重保障机制，通过K8s原生探针实现基础设施层面的健康检测。

K8s原生探针实现方式：

K8s提供了三种原生探针来监控Pod的健康状态，它们协同工作，确保服务的高可用性：

- startupProbe（启动探测）：确保服务完全初始化后再进行后续探测，适用于启动时间较长的服务。在容器启动后开始探测，只有startupProbe成功后，才会启用readinessProbe和livenessProbe。这样可以避免在服务启动过程中因为未就绪而被误判为不健康。配置时需要设置足够大的`failureThreshold`，以应对服务启动时间较长的情况。

- readinessProbe（就绪探测）：判断Pod是否准备好接收流量，这是健康检测机制的关键环节。通过调用后端服务的`/health`接口进行探测，如果连续失败（如3次），Pod会被标记为NotReady，K8s会自动切断流向该Pod的新流量。InferencePool会根据readinessProbe的结果决定是否将Pod加入可用后端列表，从而实现自动的服务发现和流量切换。探测间隔建议10-30s，超时时间5-10s，失败阈值通常设置为3次。

- livenessProbe（存活探测）：判断Pod是否还在正常运行，用于检测服务是否"假死"。如果连续失败，K8s会重启Pod。配合RAS业务监控，实现多层次的故障检测和恢复机制。探测间隔建议10-30s，超时时间5-10s，失败阈值通常设置为3次。

    后端服务Pod配置示例：

    以下是一个完整的后端服务Pod的Deployment配置示例，包含三种探针的配置：

    ```yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: inference-service
    spec:
      template:
        metadata:
          labels:
            app: inference-service
            role: serving
        spec:
          containers:
          - name: inference-service
            image: <inference-service-image>
            ports:
            - containerPort: 8000
            # 启动探测：确保服务完全初始化
            startupProbe:
              httpGet:
                path: /health
                port: 8000
              initialDelaySeconds: 15
              periodSeconds: 10
              timeoutSeconds: 5
              failureThreshold: 60
            # 就绪探测：判断Pod是否准备好接收流量
            readinessProbe:
              httpGet:
                path: /health
                port: 8000
              initialDelaySeconds: 15
              periodSeconds: 10
              timeoutSeconds: 5
              failureThreshold: 3
            # 存活探测：判断Pod是否还在运行
            livenessProbe:
              httpGet:
                path: /health
                port: 8000
              initialDelaySeconds: 15
              periodSeconds: 10
              timeoutSeconds: 5
              failureThreshold: 3
    ```

    配置要点：
    
    为了启用健康检测机制，后端服务必须提供健康探测接口。配置中通过`httpGet.path`指定健康检查接口路径（如`/health`），通过`httpGet.port`指定接口端口（需与容器暴露的端口一致）。其他参数如`initialDelaySeconds`、`periodSeconds`、`timeoutSeconds`、`failureThreshold`可根据实际服务启动时间和业务需求进行调整。

#### 请求负载均衡

请求负载均衡是智能路由的核心能力之一，用于在多个可用的后端服务Pod之间均匀分发推理请求，避免单个Pod过载，提高整体系统的吞吐量和稳定性。

本方案提供基本的负载均衡能力，支持随机路由策略。通过配置EPP的`EndpointPickerConfig`，可以指定使用随机选择器（`picker-min-random`）来实现请求的随机分发。

随机路由配置示例：

以下是一个随机路由策略的配置示例，通过Helm values文件配置：

```yaml
inferencepool:
  inferenceExtension:
    pluginsConfigFile: "epp-random-routing.yaml"
    pluginsCustomConfig:
      epp-random-routing.yaml: |
        apiVersion: inference.networking.x-k8s.io/v1alpha1
        kind: EndpointPickerConfig
        plugins:
        - type: picker-min-random                  # 随机选择器
        schedulingProfiles:
        - name: default
          plugins:
          - pluginRef: picker-min-random
```

配置完成后，EPP会根据该策略在多个后端服务Pod之间随机分发请求，实现基本的负载均衡能力。

##### 故障切流流程

1.  故障判定：监控系统检测到后端服务业务异常（如服务长时间无响应）。
2.  触发退出：触发故障处理服务的优雅退出流程。
3.  主动下线：删除故障后端服务的Pod（或触发Pod自动终止）。
4.  流量切换（关键步骤）：
    *   新流量：Pod删除后，K8s Endpoint Controller会将该IP从Service/InferencePool列表中移除，新流量自动路由到其他节点。
    *   在途流量（On-flight）：对于正在发送给故障Pod的请求，由于Pod终止或网络不可达，请求会失败。此时网关代理捕获5xx错误或连接失败，触发自动重试，将请求转发给其他健康的后端服务。

##### 服务恢复流程

1.  重启服务：拉起新的后端服务Pod。
2.  自身预热：等待Pod就绪，并通过发送推理请求自我验证服务可用性。
3.  上线接流：验证通过后，给Pod打上InferencePool匹配的Label（如`app=inference-service, role=serving`）。
4.  自动发现：InferencePool感知到新Pod，将其加入负载均衡列表，流量开始进入。

#### 请求重试

请求重试机制用于处理超时或异常的推理请求，确保系统的可靠性和容错能力。通过在网关控制面配置HTTPRoute资源，可以定义超时和重试策略，网关会根据这些配置自动执行请求重试流程。

用户需要配置一下核心参数：
*   请求超时时间：当请求超过该时间仍未完成时，网关数据面会终止请求并返回超时错误。
*   重试次数：网关数据面会根据此配置自动进行请求重试。
*   单次尝试超时时间：网关数据面会在每次重试时应用此超时设置。
*   触发重试的错误类型：包括网络连接失败和服务不可用错误（如5XX），针对这些错误进行自动重试。网关数据面会检测这些错误并触发重试流程。

配置完成后，网关控制面会将配置同步到网关数据面，网关数据面会根据HTTPRoute中的配置自动执行超时检测和异常请求重试处理，无需额外操作。
