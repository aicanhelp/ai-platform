# 5月14日 例会记录
## 与会人：崔雷雷、王清珺、张超、史子龙、徐尤红、张庆伟 
## 纪要人：张庆伟
## 会议纪要：
### 议题：
### 1、openFuyao整体介绍 和 一体机介绍
@王清珺 整体介绍了openFuyao、openFuyao-Ray和一体机规划，同步至博云侧，@崔雷雷在博云侧反馈信息，后续和博云相关技术团队人员进行其他技术方向的进一步讨论。

### 2、安装部署现状同步
经1230、330两个版本迭代，基于cluster-api的安装部署在 集群生命周期管理和多云管理方面占优，同时有管理面操作简洁。但相比installer更复杂，同时安装时间有增长。需进一步优化性能，提升易用性。

### 3、安装部署近期630方案
**①效率优化**
对安装时间占比进行了梳理分析，对于cluster-api需要安装引导节点、管理集群和业务集群 3层安装步骤较重，时间增加的情况，进行处理。对轻量化场景，达成一致：即不再通过管理集群来布置后续业务集群，管理集群直接作为业务集群使用。在引导节点上封装集群生命周期管理面。
后续时间优化可以考虑：
将双架构镜像改成单镜像架构，减少总体镜像的大小和拉取时间。 
离线安装支持用户选择所需的扩展组件，减少拉取不必要的包，可以考虑主包和patch包的方式。
以及调研其他安装部署工具的整体时间，进行整体衡量评估。

**②存储插件选择**
@张超 建议，开源版本 存储插件的选择和扩缩容能力与openshift开源版okd对齐，商业化的方案交给伙伴进行处理，形成商业解决方案。
目前调研发现openshift开源版本okd默认安装时仅提供 Kubernetes 原生的 PV/PVC 框架和 CSI Operator，并不附带具体的存储后端插件。用户使用根据需要手动部署本地存储或第三方分布式存储。包括腾讯的开源容器平台TKE 本身也不提供存储功能，是通过集成云原生的存储应用或通过存储扩展组件的方式，对接用户存储设施。okd提供扩缩容能力，目前没有发现提供存储上的特殊说明。
调研结论：开源版本不提供具体的存储解决方案，可以对缩容功能进行提示，如需稳定使用，用户需自行接入存储插件。

**③前置校验模块**
在installer-service中添加节点前置校验模块

**④状态呈现**
直接修改cluster-api-bke-provider，加入对openFuyao核心组件pod状态的判断。并讨论了Manage纳管状态的出现的原因和应对办法。

### 4、后续规划
- 基于Bke的使用反馈，后续进一步优化

  1、将err部分打出来，不直接返回。
  2、集群创建失败时进行删除，存在卡死现象 和 异常场景下bke-provider该pod重启的逻辑梳理。
  3、时间同步ntp问题。
  4、确认是否要重构，bkecommon 拆到各个仓里。
  5、event事件持久化。

- 长久规划

  1、对接官方的三个provider
  2、cluster api core中加入addon
  3、支持使用安全容器iSulad等作为容器运行时
