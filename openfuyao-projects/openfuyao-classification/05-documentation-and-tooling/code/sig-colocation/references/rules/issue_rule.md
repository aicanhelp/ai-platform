# **1. 问题单级别定义原则**

| 级别 | 定义                                                         |
| ---- | ------------------------------------------------------------ |
| 致命 | 产品的关键功能和性能不符合用户要求，或由于设备质量原因、按资料指引造成业务中断、频繁瞬断或服务质量严重下降等可能给用户收益或声誉造成较大损失的问题。对于安全漏洞采用CVSS（Common Vulnerability Scoring System）评估严重定级。若CVSS Base Score在9.0-10.0则映射为致命。 |
| 严重 | 在产品规格书或行业标准规定的条件范围内，系统的主要功能和业务性能不符合用户要求，或不能稳定运行，但仍然可以向用户提供基本的业务，或按照资料无法完成系统的重要功能和业务。对于安全漏洞采用CVSS（Common Vulnerability Scoring System）评估严重定级。若CVSS Base Score在7.0-8.9则映射为严重。 |
| 一般 | 部分次要功能失效或性能略有降低，但不会造成用户收益或荣誉受损失，或按照资料指引无法完成系统的次要功能和业务。对于安全漏洞采用CVSS（Common Vulnerability Scoring System）评估严重定级。若CVSS Base Score在4.0-6.9则映射为一般。 |
| 提示 | 系统功能可以正常运行，但存在不影响功能正常完成的操作、理解上不合理的问题。对于安全漏洞采用CVSS（Common Vulnerability Scoring System）评估严重定级。若CVSS Base Score在0.1-3.9则映射为提示。 |

# **2. 问题单处理原则**

## **问题单状态**

| 问题单状态 | 描述                                                         |
| ---------- | ------------------------------------------------------------ |
| 开启       | 当前问题单待修改                                             |
| 待测试     | 问题单修复的代码已提交，待测试进行验证。该状态仅允许测试人员配置。 |
| 挂起       | 问题超过一个月未复现，经过评审后可设置为挂起，在后续版本修复 |
| 已解决     | 经测试验证问题已解决，可将待测试状态修改为已解决             |
| 转需求     | 当问题单需要作为需求处理时，经CCB、RAT评审后可修改状态为转需求。该状态问题单不计入问题单总数。 |
| 重复问题   | 当已有相同问题的问题单时，可将当前问题单状态修改为重复问题，评论内附上对应问题单链接。该状态问题单不计入问题单总数。 |
| 非问题     | 经评审不是问题的问题单，可将状态转为非问题，问题单附上评审结论。该状态问题单不计入问题单总数。 |



## **问题单关闭的条件**

问题单必须通过回归测试，验证问题已经解决，并且没有引入新问题的情况下才能正常关闭。关闭问题单只能有四种情况：问题解决关闭，非问题关闭，重复问题关闭，纳入新需求关闭。

凡是经过确认是设计质量问题，但没有解决的原则上不允许关闭。如果因无法重现、无法解决等情况，决定暂不处理的，可以挂起（包括永久挂起）。

对于因重复（一般指缺陷原因相同，少部分情况下问题现象可能不同的共因问题）而关闭的问题单，需要在问题单中增加重复问题单单号，以及重复问题单修改对应的pr链接，重复问题单不应有新pr合入。

纳入新需求关闭时，需要提供CCB和RAT转需求的评审结论。

对于采用规避措施来减缓或消除问题的情况，如果规避措施经过测试后，证实可以保证用户不再看到问题现象，且该规避措施按照正式有效的途径发布执行后，该有关规避措施可以视为有效解决手段，并关闭问题。如果规避措施只能部分解决问题，而不是彻底解决（从用户角度消除）问题，则该规避措施不能视为正式解决，问题单不能关闭。

## **问题单挂起的条件**

符合下列情况之一的问题单，经过评审决策后，可设置为“挂起”状态，其他需要以版本遗留问题处理，不能使用挂起：

1.超过1个月未能重现的问题，但是总时长不满足降级。

2.当前版本无法解决，或解决成本较高，计划在下个版本解决，且问题单级别为非“严重”的问题。

满足下列条件可认定为“问题解决成本较高”：如果问题单解决需要修改历史代码，且历史代码存在于上个LTS版本，修改会引发质量风险时。

## **问题单降级的条件**

提单人和审核人无争议降级可以直接由提单人进行降级，并详细描述降级理由：

如果提单人或审核人不同意降级，必须在评审会议中评审通过同意降级，记录会议结论，问题单中增加会议结论链接。

长期不重现降级：超过一个月不重现可经评审会议评审降级。 降级为提示单后再连续一个月不重现且总重现时长超过三个月的可申请评审会议评审关闭（也可设置为挂起）。

## **当前版本不解决的问题**

当前版本决定不解决的问题，必须在新版本中验证解决后才能关闭原问题单。

## **问题的规避措施**

问题无法彻底解决时，如果能够通过非人工干预的规避措施避免问题发生且经过CCB评审通过，可视为问题解决。

## **问题单转需求的处理方式**

所有转需求的问题单需要经过评审会议评审，记录会议结论。问题单中需要增加评审会议结论。

## **问题单处理时间原则**

| 处理环节           | 时间指标 |
| ------------------ | -------- |
| 阻塞问题定位响应   | 1小时    |
| 非阻塞问题定位响应 | 3小时    |
| 阻塞问题解决       | 2天      |
| 非阻塞问题解决     | 4天      |

# 3. 问题单处理流程（内部）

## 提单

1. 标题要以【XXX】开头，括号中指明问题单对应特性名
2. 问题单需要填写问题发生环境信息、问题描述、重现步骤、期望结果、实际结果等信息，具体见问题单模板。
3. 问题单需要附上版本标签及问题单类型标签，例如“集成测试”+“v24.06beta1"。
4. 问题单需要添加责任人（具体开发者），必要时可添加协作人（特性owner或相关责任人）
5. 问题单需要填写问题单级别，分类原则见上文。
6. 问题单需要关联具体仓库
7. 问题单需要指定修改时间范围，时间范围划分见上文时间原则。
8. 提单时需要在问题单中关联对应测试用例及需求。

## 改单

1. 提PR时关联到问题单对应issue（该步骤需要进入企业工作台，在企业内pr页面操作）。
2. 在问题单内评论中附上自测结果相关截图，由开发人员将问题单状态由开启修改为待测试。
3. 测试人员在测试环境验收新合入代码无误后可将问题单状态由待测试改为已解决，仅测试人员可将问题单修改为已解决。
4. 如果验收不通过需要将问题单打回，将问题单状态由待测试改为开启，将验证结果结论或相关截图上传到问题单评论中。
5. 具体关联仓库需要有开发人员进行审视及修改。
6. 当开发及测试意见不一致时可找测试经理及责任田主进行确认，如果意见仍有分歧则上升至CCB上进行评审，并将评审结论附到问题单评论中。
