# 提交消息
## 代码再次提交采用追加方式
```
git commit -a --amend -m"xxx"
git push origin -f dev_branch
```
## 代码冲突处理
代码冲突,先更新master,再rebase,解决冲突后再提交
```
git rebase master
git commit ...
git rebase --continue
```
## 使用下面的指南来帮助制作格式良好的提交消息
- 尽量将主题行控制在 50 个字符以内；不超过 72 个字符
- 提交消息主题中的第一个单词应大写，除非它以小写符号或其他标识符开头
- 不要以句点结束提交消息主题
- 在提交消息主题中使用祈使语气
- 在提交消息正文之前添加一个空行
- 将提交消息正文包裹在 72 个字符处
- 不要在提交消息中使用 gitee 关键字或 (@) 提及
- 使用提交消息正文来解释提交的内容和原因
### 尽量将主题行控制在 50 个字符以内；不超过 72 个字符
提交消息主题行的 50 个字符限制是保持消息摘要尽可能简洁的重点。它应该足以描述正在做什么。

72 个字符的硬性限制是为了与最大正文大小保持一致。当使用查看存储库的历史记录时git log，git 会用额外的空格填充正文。
将宽度换行为 72 个字符可确保正文文本居中并在 80 列的终端上轻松查看。

### 提供额外的背景信息
可以通过在提交消息中添加PR 所影响的类型或区域作为前缀，以更少的字符提供更多上下文。

例子：
```
cleanup: remove unused portion of script foo
deprecation: add notice for bar feature removal in future release
etcd: update default server to 3.4.7
kube-proxy: add a test case for HostnameOverride
```
在进一步扩展提交消息正文中的内容和原因之前，这些可以作为一个很好的主题。

### 提交消息主题中的第一个单词应大写，除非它以小写符号或其他标识符开头
提交消息主题就像一个缩写句子。第一个单词应大写，除非消息以符号、缩写词或其他标识符（例如通常为小写的种类或区域）开头。

### 不要以句点结束提交消息主题
这主要是为了节省空间，但也有助于使主题行尽可能简短。

### 在提交消息主题中使用祈使语气
祈使语气可以被认为是“发出命令”；这是一个现在时的陈述，明确描述了正在做什么。

好的例子：
- 修复 y 中的 x 错误
- 将 foo 添加到 bar
- 恢复提交“baz”
- 更新拉取请求指南

坏例子
- 修复了 y 中的 x 错误
- 将 foo 添加到 bar
- 恢复错误的提交“baz”
- 更新拉取请求指南
- 修复更多问题

Chris Beams关于形成命令式提交主语的一般准则是它应该完成这句话：
```
If applied, this commit will <your subject line here>
```
例子：
- 如果应用，此提交将修复 y 中的 x 错误
- 如果应用，此提交会将 foo 添加到 bar
- 如果应用，此提交将恢复提交“baz”
- 如果应用，此提交将更新拉取请求指南

### 在提交消息正文之前添加一个空行
Git 使用空行来确定提交消息的哪一部分是主题和正文。空行前面的文本是主题，后面的文本被认为是正文。

### 将提交消息正文包裹在 72 个字符处
git 的默认列宽是 80 个字符。当查看 git 日志时，Git 会在消息正文的文本中添加 4 个空格。这将为您留下 76 个可用的文本空间，但文本将是“不平衡的”。
为了使文本居中以便更好地查看，另一侧人为地填充了相同数量的空格，从而每行有 72 个可用字符。将它们视为 Word 文档中的页边距。

### 不要在提交消息中使用 gitee 关键字或 (@) 提及
gitee关键词:在提交消息中使用gitee关键字，后跟`#<issue number>`引用会自动将`do-not-merge/invalid-commit-message`标签应用到您的 PR，防止其被合并。

PR 中用于关闭问题的gitee关键字被认为是一个方便的项目，但在提交消息中使用时可能会产生意想不到的副作用；经常关闭一些不应该关闭的东西。

被屏蔽的关键词：
- close
- closes
- closed
- fix
- fixes
- fixed
- resolve
- resolves
- resolved
### (@)提及
提交消息中的 (@) 提及将向该用户发送通知，并且每次更新 PR 时都会继续这样做。

### 使用提交消息正文来解释提交的内容和原因
提交及其提交消息是PR 中所做更改的“永久记录” 。描述某些事情发生变化的原因以及可能产生的影响。你正在向您的审阅者和下一个必须接触你代码的人提供上下文。

如果某些内容正在解决错误或响应特定问题，你可以将其链接到消息正文本身作为参考。在追踪未来的错误或回归时，这些类型的面包屑变得至关重要，并进一步帮助解释进行提交的“原因” 。
