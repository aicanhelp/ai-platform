## 概括

容器场景下， 各种负载对OS运行环境的依赖得到很大减少，但容器平台自身反因负责内容更多而对OS运行环境有了更多依赖，本提案拟提供一个单机检查工具，在openFuyao场景下检查特定运行环境是否满足容器平台的环境诉求，以减少各种因环境依赖造成的部署失败或功能失效的场景。

## 动机

### 背景和问题

作为一个开源的生态，Linux发行版数量众多，参考[LinuxTimeLine](https://github.com/FabioLolix/LinuxTimeline), 当前已有数百个公开的Linux发行版，而企业内部基于某发行版定制的内部使用版本更是不计其数，数量众多的Linux发行版给运行于其上的应用带来了挑战，为了统一Linux的生态，早在2001年，Linux基金会就发起了LSB项目，而LSB项目自2015年LSB5.0发布后已再无活动，LSB项目已事实停止，各发行版也不再进行LSB认证，但各发行版配置和能力不一致的问题并未消失。

另一方面2013年容器技术的诞生，容器镜像自身打包了整个容器运行依赖的环境，降低了对下层操作系统的依赖，实现"build once，run anywhere"。而CaaS平台本身作为容器运行和编排的基础，自身无法完全运行于容器中，同时容器平台需要负责网络和存储相关能力，对系统的配置和特定内核模块的依赖也无法消减。

openFuyao作为一个开放生态的系统，除当前已明确支持的openEuler、Ubuntu系统外，也可能会运行在其他各种Linux发行版系统上，再考虑到各生态伙伴自己构建的私有Linux版本，如何保证这些运行环境能够满足openFuyao的正常运行，是openFuyao生态健康发展必须要考虑的问题。

### 可能解决方案分析

#### 对OS依赖分析

##### 内核能力依赖

用户态与内核态通信接口在不同版本的兼容性分析如下:

- 系统调用  
  系统调用是主要的用户态和内核态交互接口，linux的系统调用很稳定，参考系统调用相关文档，最近一次的系统调用删除为5.5版本删除_sysctl，该调用2011年后即无人调用，最终删除。在上一次则为3.16版本。基本可以认为系统调用是稳定的。
- procfs  
   对比4.4~6.1版本内核，procfs变更主要是新增文件、新增字段，可以认为procfs是前向兼容的
- sysctl和/proc/sys  
  sysctl和/proc/sys在不同的版本间变更的内容较多，同时，由于各发行版定制的内核能力，不同的发行版间也有所区别
- sysfs
  sysfs用于将设备和驱动信息导出到用户空间，也支持修改和调整，从4.4到6.1，sysfs有诸多增删和变更
- netlink、relayfs、debugfs、ioctl  
  一般用于涉及到内核模块开发相关，三方扩展较多，兼容性变化较大，但基本机制没有调整较少。
- 内核模块及内核能力  
  非直接接口，但依赖加载的某些内核模块能力
而容器平台对上述依赖主要是系统调用、procfs读取、sysctl的配置调整，其他内容依赖较少。

##### 非内核能力依赖

- 工程依赖  
  工程依赖指部署、升级及对OS的配置对OS的依赖，如: 用户管理、磁盘管理、网络配置等，主要依赖内容为配置文件及配置路径、基础的shell命令等
- 运行依赖  
  运行依赖主要是对系统so的依赖，这部分依赖可以通过静态编译消减，也可以通过检查是否存在对应so版本方式

#### 整体适配策略

1. openFuyao尽量缩减对非内核的主机侧内容的依赖:
    - 尽量打包为容器应用，减少主机进程
    - 通过静态编译等方式缩减对so的依赖，以减少so变更带来的风险
2. 提供一个兼容性检查工具，检查CaaS平台是否能够在目标环境正常运行，并给出不符合点以期使用人员进行调整

### 配置及接口形式

#### 检查项配置

检查项组织结构如下:

@startuml

object "检查集" as checkset{
    名称
    包含的检查集清单
    检查项列表
}

object "检查项" as checkitem{
    名称
    说明[说明]
    运行参数
    期望值[可选]
    实际值[可选]
    子检查项列表[可选]
}

object "子检查项" as subcheckitem{
    名称
    说明[说明]
    期望值[可选]
    实际值[可选]
}

checkset o-- checkset

checkset o-- checkitem

checkitem o-- subcheckitem

@enduml

检查集本身支持嵌套，以满足openFuyao内各组件的嵌套关联。

##### 检查集及检查项

```yaml
name: kubernetes #名称
desc: 本检查项针对kubernetes运行环境进行检查
include:   #包含的检查集
  - openEulerBase 
  - kubernetes

items:    #检查项
  - sysctl-check

```
其中:
- include: 用于指定包含的检查集
- items: 指定直接包含的检查项，此检查集的所有检查项包含如下两部分中的检查项组成的合集
    - include中的检查集中指定的检查项
    - items中指定的检查项


检查项格式定义
```yaml
name: the_name_of_checkitem   #检查项名称
desc: description 
params:
  - name: param_name
    desc: param_desc
    default: default_value_of_param
    multi: false
kind: kv-checker
doc: |
   通过sysctl -a命令检查sysctl是否符合kubernetes运行要求
spec:  # spec中的内容都是直接传递给对应的检查项实现插件的
  source:  #指定数据源，支持command、file，其中的每行数据都被splitter分割为key、value
    command:
      - sysctl -a
  kvParser: #可选，指定如何从source中解析出key和value，如果不指定，则默认使用空字符进行拆分。如果拆分呢失败，则跳过该行
    reSplitter: = # 使用正则表达式拆分key、value
  subItems: #子检查项
    - name: kernel.threads-max
      key: kernel.threads-max  #如果指定了key，则使用key匹配， 否则直接使用name，key本身支持正则表达式进行通配
      type: int-range  #整型值范围
      expect: "[409600,)"
      doc: 最下线程数<409600，可能导致系统无法正常运行 
```

各字段含义:
- name: 指定检查项名称，checkset可以通过name字段引用对应的检查项
- desc: 检查项描述。报告和帮助信息中也会呈现此信息。
- params: 参数，可以在后面检查项中以`{{param_name}}`方式引用， 只能指定到结果字段的值中。  
  这个参数可以从命令行中以-p方式指定，如果不指定则默认取值default。为避免多个参数名称重复，当在界面上指定数值时，可以以 `检查项名称:参数名称=参数值`形式指定参数取值，如此该参数仅会指定到此检查项上如果不指定`检查项名称`前缀。其中，multi字段用于指定该参数是否可以多次绑定，也就是具体检查项将会收到一个参数值列表。
其中，kind: 指定检查项类型，实际上就是检查插件类型，后续的spec字段实际是传递给检查插件的信息，默认支持如下检查插件

- **kv-checker**: 将数据源(命令或文本)拆分为key、value形式，并检查特定的key是对应的value是否符合预期
- **kernel-module-checker**: 检查对应的内核模块是否存在，配置参数是否符合要求
- **command-checker**， 执行命令并检查返回是否为0，为0则成功，否则失败
- **ping-checker**, 与目标节点执行ping命令，如果能成功则为成功，否则失败

###### kv-checker

```yaml

spec:
  source:  #指定数据源，支持command、file，其中的每行数据都被splitter分割为key、value
    command:
      - sysctl -a
  kvParser: #可选，指定如何从source中解析出key和value，如果不指定，则默认使用空字符进行拆分。如果拆分呢失败，则跳过该行
    reSplitter: = # 使用正则表达式拆分key、value    
  subItems: #子检查项
    - name: kernel.threads-max
      key: kernel.threads-max  #如果指定了key，则使用key匹配， 否则直接使用name，key本身支持正则表达式进行通配
      type: int-range  #整型值范围
      expect: "[409600,)"
      doc: 最下线程数<409600，可能导致系统无法正常运行
        
```

spec各字段含义:

- spec.source  【必选】 指定检查的数据源，支持file, command
  - file: 以文件作为数据源，如果指定多个并且解析后key有重名，则后出现的优先级为高
  - command: 以命令执行结果作为数据源，会合并stdout、stderr

- spec.kvParser
    将前序数据源拆分为key，value形式，并在subItems中对key、value进行匹配处理。如果不指定，则默认使用正则表达式`[ \t]*`进行拆分
  - reSplitter:  指定正则表达式拆分
  - reGroup: 指定正则表达式分组进行拆分，如果有多于两个group，则使用中划线连接前面的group匹配值作为key，最后一个group作为value
- spce.subItems:
    子检查项
  - name: 【必选】子检查项的名称, 输出的报告中的子检查项名称也是此值，如果不指定key，name同时充当key
  - key： 【可选】  用于匹配对应的key，支持正则表达式进行通配，如果使用正则表达式，则需要以re:开始
  - type\&expect:  字段类型和期望结果，支持如下形式:
    - int-range: 整形范围，使用区间上向限方式制定，可以省略上下限，表示没有限制
    - int: 数值
    - str: 字符串强匹配，将会被trim掉空字符(空格、\\t)后使用
    - version-range: 版本号范围，version为点分形式，如`[1.0.1, )`, 表示版本大于等于1.0.1
    - regex: 正则表达式，要求value能够匹配该正则表达式
- spec.doc 【可选】 输出到报告中用作说明
- 用来支撑如下检查能力
  - sysctl检查，可以使用sysctl -a命令作为source
  - systemd状态检查，可以使用systemctl show <服务名>方式作为source
  - limits检查，通过/etc/security/limits.conf或/etc/security/limits.d下的文件配置作为数据源

###### kernel-module-checker

 **kernel-module-checker**: 检查对应的内核模块是否存在，配置参数是否符合要求。格式定义如下:

```yaml
spec:
  - name: ip_vs #【必选】内核模块名
    detail: # 【可选】内核加载参数及其他
    - name: parameters/conn-tab_bits
      type: int-range
      expect: "[0, )"
    doc: 容器网络依赖ip_vs
```

spec各字段说明:

- `spec.[items].name`: 【必选】模块名
- `spec.[items].detail` 【可选】，制定具体的加载参数
  - name: 【必选】，如果有detail，则name必选，指定具体的加载参数名，name为具体的路径
  - type: 同kv-parser
  - expect: 同kv-parser

###### command-checker

 执行一个命令并检查返回值及输出

```yaml
spec:
  - name: echo command exist  #【必选】 名称
    command: which echo
    doc: 检查{name}命令是否存在，配置过程依赖echo命令  
```

spec各字段说明:

- `spec.[items].name`: 【必选】检查项
- `spec.[items].command` 【必选】执行的命令和参数
- spec.doc 【可选】 输出到报告中用作说明
- spec.[items].type & expect 【可选】，同kv-parser, 如果不指定，则直接使用上述命令的返回值作为判断，0为成功，非0失败。否则按照expect检查stdout


###### ping_checker
通过ping命令，检查网络连通性，输出与各节点的连通性检查结果，每个节点一行，

```yaml
params:
  - name: ping_ip_list
    desc: 待ping的目标节点，可多次绑定，也可以一次绑定，绑定方式如下 -p ping_ip_list=ip1@nodename1,ip2@nodename2, 其中nodename可以不指定，如果nodename中本身带有`@`或`,`，则需要采用多
    次绑定的方式。
    multi: true
spec:
  targets:  {{ping_ip_list}} 
```

字段说明:
- targets: 待ping的目标参数，实际为一个列表，可以使用ip@nodename形式指定具体的目标，也可以通过命令行参数形式指定。
- params: 支持通过-p指定ping的目标。具体的参数形式为 `ip@nodename1,ip2@nodename2name`, 其中:
    - 使用`ip@nodename`的形式指定，第一个@符号前为ip地址，后续内容则为节点名, 也可以不指定节点名
    - 使用`,`分割多个目标，如果界面名中本身包含`,`或`@`，则需要通过参数多次绑定的形式来指定参数值


#### 扩展插件定义
