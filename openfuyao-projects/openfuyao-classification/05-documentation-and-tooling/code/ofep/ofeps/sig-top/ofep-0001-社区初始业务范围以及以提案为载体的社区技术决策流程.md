# oFEP-0001：社区初始业务范围以及以提案为载体的社区技术决策流程

## 发布签核清单：

openfuyao/ofep/sig-top/ofep-0001-社区初始业务范围以及以提案为载体的社区技术决策流程.md

## 摘要:

本提案描述openFuyao社区的技术范围，并且通过oFEP（openFuyao Enhancement Proposal）来规范社区技术决策流程。

## 动机:

社区的技术演进面临许多挑战：

- 社区技术范围不明确，导致讨论边界不清
- 许多技术提案虽然反复通过邮件列表，社区会议，issue等讨论，但是缺乏决策过程；同时技术性描述多，价值主张描述少
- 历史分析过程难以回溯，造成信息丢失，或者某些提案反复分析
- 技术提案的讨论很分散，难以保证质量，同时提案的结构化逻辑不足，分析不全面

参考其他成熟的社区，比如k8s，rust等，都通过社区定义的一系列文档来承载技术演进决策，这些文档公开可查，可参与讨论，使得社区开发人员对技术发展的脉络，将来的走向，都可以有充分的理解。

openFuyao 需要学习这些成功的经验，定义一套适合 openFuyao 的文档与流程规范。

## 方案的详细描述：

### 社区的技术范围

随着云原生与AI的演进，面临着许多挑战：算力爆发式增长，当前硬件百花齐放，但软件生态不足；云原生时代的微服务架构与AI的负载特征不完全匹配；AI对软硬件的可靠性更加敏感进一步推高了软件工程的复杂度。

为解决这些挑战，openFuyao社区的定位为多样化算力集群软件生态社区，聚焦多样化算力集群使能与调度、场景化加速、多层次应用货架打造社区技术体系。

  ```mermaid
  graph LR;
  subgraph 多样化算力集群使能与调度;
  A[容器编排];
  B[多样化算力调度]
  end
  subgraph 场景化加速;
  C[AI推理场景];
  D[大数据场景]
  end
  subgraph 多层次应用货架;
  E[CNI/CSI/CRI<br>/Operators...];
  F[开箱即用<br>解决方案]
  end
  ```


- **多样化算力集群使能与调度**：重点赋予现有的云原生架构异构算力的统一编排能力，和更精细化的感知和调度能力；具体的能力包括多样化异构算力池化 、超大规模集群、安全容器、近实时度量、敏捷调度、灵活扩缩容、冗余&自愈等。
- **场景化加速**：围绕当前热门技术趋势，基于AI推理场景与大数据场景，探索场景化加速能力。具体能力如多层次KVCache、通信加速、智能路由、近实时计算、存储加速等。
- **多层次应用货架**：社区提供多层次的软件货架，相关能力可以组件级发布，或者以最佳集成实践，如容器平台发行版，AI推理一体机发行版等形式发布。

### oFEP 的目标读者
 oFEP 目标读者是 openFuyao 社区当前和未来的开发者，实践者和技术决策者。oFEP 不是技术推广、宣传文档。

### oFEP 生命周期流程

  以下用流程图表示 oFEP 的生命周期状态图

  ```mermaid
  flowchart TD;
  A[提交oFEP PR] --> B[provisional];
  B --> |提交决策|C{技术委员会决策};
  C --> |批准|D[implementable];
  C --> |需要修改|B;
  C --> |拒绝|I[rejected]
  D --> |功能实现|E[implemented];
  E --> |提案已过时或有更好的替代方案|F[replaced];
  B --> |主动撤回|G[withdrawn];
  B --> |长期不推进|H[defferd];
  ```

oFEP状态说明：

- **provisional**：初始提案阶段，此时尚未确定是否推进，社区还在讨论中，当社区达成一致时（至少一名TC成员共同主张该提案），可以提交技术委员会决策，按照社区运作章程，需要2/3（含）成员投赞同票，则认为决策通过。

- **implementable**：已过得技术委员会批准，可开始开发和实现。

- **implemented**：已经开发何如代码仓，并且在openFuyao某个版本发布。

- **deffered**：推迟处理，暂时不考虑实现。

- **rejected**：提案被社区拒绝，不会推进该提案。

- **withdrawn**：作者主动撤回提案。

- **replaced**：提案已过时，有更好的替代方案。更新为此状态时，需要同步更新replaced-by元数据字段，指向新的oFEP。

### oFEP类型

所有影响社区演进的相关提案，都应该以oFEP承载，这些提案可能包括：

- 新成立一个SIG的提案：对于社区当前未覆盖的技术领域和方向，贡献者可以申请成立特别兴趣小组（SIG）；
- 针对某个SIG新增项目提案：社区以项目群方式运作，各SIG组可以新增对应的部件项目，或者准解决方案级（如容器平台发行版，AI一体机发行版）的项目，可以通过oFEP对SIG新增相关项目。
- 针对已有SIG的特性增强提案：在SIG下的某个项目中实现某些特性功能，可以提交特性提案；
- 针对社区流程，管理机制的提案：针对社区的管理流程优化，希望在社区达成一致共识的相关优化建议，同样通过oFEP承载；
- 社区版本提案：社区某个版本交付的范围，特性清单，交付节奏，时间节点，同样以oFEP形式呈现，同时，版本包含的特性清单，应该是一个oFEP清单，描述各个特性的实现内容；

### oFEP 格式要求

 提交的oFEP文件名应当以 "ofep-XXXX-提案标题"明明，XXXX 为当前未被占用的最小四位数字编号。
 oFEP 应以 Markdown 格式写作，格式参考[0000-ofep-templete.md](https://gitcode.com/openFuyao/ofep/0000-template.md )。
对于技术类特性级的提案，社区的最佳实践是建议实现模板中的所有必填字段，对于成立SIG的提案，社区路程机制类提案，版本规划提案，应该至少包含摘要，动机，提案等核心内容。

### oFEP 的开发和管理

 oFEP 统一以 PR 形式提交到 [https://gitcode.com/openFuyao/ofep](https://gitcode.com/openFuyao/ofep) 仓库中，仓库下以sig划分目录，提交到对应的sig目录下，对于社区公共类提案，如社区流程，机制等，提交到sig-top目录下。

oFEP修订说明：

- 处于 **provisional** 状态的 oFEP 文件可以被反复大规模修订；
- 处于 **implementable**，**implemented**，**replaced** 状态的 oFEP 文件可以接受定期，小规模修订；针对implementalbe的oFEP，表明相关特性进入开发交付状态，此时建议建立一个isse来管理和讨论oFEP的交付进展状态。
- 处于**rejected**，**withdrawn** 状态的 oFEP 不接受修订；
- 处于**deffered**状态的oFEP，可以修订为"provisional"状态重新启动讨论；

社区逐步建立一套oFEP的管理办法，包括合入时的门禁检查，oFEP的状态度量看板等，相关基础设施配合oFEP的管理办法配套建设。
