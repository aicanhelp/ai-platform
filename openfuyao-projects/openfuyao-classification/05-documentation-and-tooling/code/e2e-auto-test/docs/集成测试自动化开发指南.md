# 集成测试自动化开发指南

参考：

- Pytest 官方文档：[https://docs.pytest.org/](https://docs.pytest.org/)
- Playwright 官方文档：[https://playwright.dev/python/](https://playwright.dev/python/)

## Pytest

### 项目结构

pytest 测试框架中，测试代码按层级组织，最多可以分为以下四个层级：

- 方法/函数：最小测试单元，包含具体的运行与断言逻辑。需要以 `test_` 开头才能被 pytest 识别。
- 类：定义在模块中的类，用于组织相关的测试方法。一个测试类可以包含一个或多个测试函数，每个测试函数都是一个独立的测试用例。测试类可以包含共享的前置/后置方法、辅助方法等。通常以 `Test` 开头。
- 模块/文件：单个 Python 模块/文件，可以包含一个或多个测试函数、测试类。测试文件需要以 `test_` 开头或 `_test` 结尾才可被 pytest 识别。
- 项目：一个测试项目除了包含上述测试代码，还需要包含配置文件。如项目根目录下的 `conftest.py` 文件，该文件可以包含全局的 fixture、hook 函数、插件等。

```plain
# 典型pytest项目结构
项目 (Project)
│
├── 模块/文件 (Module) —— test_*.py
│   │
│   ├── 类 (Class) —— Test*
│   │   │
│   │   └── 方法 (Method) —— test_*
│   │
│   └── 独立函数 (Function) —— test_*
│
└── 配置文件（如 conftest.py）
```

### fixture

fixture 是一个 Python 装饰器函数，能够为测试函数运行前提供前置操作，并在测试函数运行后清理前置操作。当某个**测试函数**（非测试函数无法使用）包含一个与 fixture 同名的入参时，pytest 会自动调用该 fixture 函数，并将其返回值作为参数传递给测试函数。任何调用该 fixture 的**测试函数**中，fixture都会生效（非测试函数不生效），因此在多个测试用例相同前置操作时，调用 fixture 能有效减少重复代码。

下面的示例声明了一个 `pw_page` fixture，访问了 Playwright 官网，当该 fixture 在 `test_has_title` 中被调用时，将提供一个已经跳转到 `https://playwright.dev/` 的 Page 对象作为该测试函数的入参，且在函数运行结束后，上述 Page 对象将被关闭以节省资源。

```python
@pytest.fixture(scope="function")
def pw_page(page: Page):
    page.goto("https://playwright.dev/")
    yield page
    page.close()

# 使用自定义 fixture pw_page
def test_has_title(pw_page: Page):
    expect(pw_page).to_have_title(re.compile("Playwright"))
```

fixture 分别四个级别，通过在函数装饰器 `@pytest.fixture(scope=<level>)`声明：

- `function`：在每个测试函数前后运行（默认级别）
- `class`：在每个测试类运行前后运行
- `module`：在每个测试模块运行前后运行
- `session`：在测试会话开始与结束时调用运行

当多个测试函数需要**使用值相同的多个副本时**，应当使用 function 级 fixture，保证其相互独立，如不同用例所运行于的前端页面、一次性的测试用工作负载等。若多个测试用例需要**共用一个对象，或存在多个测试函数只需执行一次的前置操作**，则建议根据其作用范围声明 class 或 module 级 fixture，如 ssh 客户端对象（避免反复创建、连接与断开）、登录验证信息存储（无需反复登录）。

> 注意：fixture 遵循延迟执行原则，session、module、class 级 fixture 并非在 pytest 启动时、相应的模块与类开始运行时被触发，而是在范围内第一个调用它的函数开始运行时被触发。若需要一开始就触发，则需要在声明时添加 `auto_use=True`。

```python
@pytest.fixture(scope="session", auto_use=True)
def login():
    # do login
```

### 全局配置

`conftest.py` 是 pytest 的核心文件，在其中定义的 fixture、hook 函数和插件配置可以被目录下的其他测试模块使用，如 session 级 fixture、多个文件会用到的 module fixture、公用方法等，建议写在这里。

`pytest.ini` 是 pytest 的全局配置文件，用于定义命令行参数、运行配置等。pytest 将从运行路径向上查找并使用最近的 `pytest.ini` 文件。

## Playwright

### 编写测试

一个典型的测试函数包含以下步骤：

- 导航：跳转到目标页面
- 交互：定位目标元素，并进行操作
- 断言：验证页面或元素的状态或内容是否符合预期

### 常见对象

Playwright 中，Browser、BrowserContext、Page 是最常用的对象，分别对应浏览器实例、上下文实例、页面实例，组成了一个 `浏览器 -> 浏览器窗口 (Window) -> 标签页 (Tab)` 的层级关系。

```python
browser = playwright.chromium.launch()  # 创建浏览器实例
context = browser.new_context() # 创建上下文实例
page = context.new_page()   # 创建页面实例
page.close()    # 关闭页面实例
context.close() # 关闭上下文实例
browser.close() # 关闭浏览器实例也会自动关闭其下的页面和上下文实例
```

其中，**上下文**提供一系列配置项，允许我们控制一部分浏览器的状态或行为。可以在创建上下文时声明或创建后添加，常用的配置项包含：

- `base_url`: 上下文的基础 URL，配置后允许后续使用相对 URL 进行定位。
- `viewport`: 自定义视口大小，用于模拟不同的设备分辨率。
- `storage_state`: 存储登录状态的本地文件，用于模拟登录状态。
- `ignore_https_errors`: 是否忽略 HTTPS 错误，默认值为 `False`。设为 `True` 时，会忽略 HTTPS 证书错误。

```python
context = browser.new_context(
    base_url='https://example.com',
    viewport={'width': 1920, 'height': 1080},
    storage_state='storage_state.json',
    ignore_https_errors=True,
)
```

对上述的常用对象，playwright 库提供了一系列默认 fixture，以下是一些常用的 playwright fixture：

- `browser_context_args`: 浏览器上下文参数，用于覆盖默认上下文配置
- `browser`：基于 `browser_context_args` 创建的浏览器实例
- `context`：基于 `browser` 创建的上下文实例
- `page`：基于 `context` 创建的页面实例

```python
# 使用自定义的上下文配置覆盖默认配置
@pytest.fixture(scope='session')
def browser_context_args() -> dict[str, Any]:
    return {
        "base_url": "https://playwright.dev",
        "viewport": {'width': 600, 'height': 800},
    }

# 这里的 page 是基于上述自定义上下文配置衍生出的页面实例
def test_has_title(page: Page):
    page.goto("/docs/intro")
    expect(page).to_have_title(re.compile("Playwright"))
```

### 元素定位

Playwright 提供了多种元素定位方式，包括经典的选择器定位:

- `page.locator()`：根据选择器定位元素，返回一个 Locator 对象，支持多种选择器语法，如 CSS 选择器、XPath 表达式等。

    ```python
    page.locator('.login')
    page.locator('input[name="username"]')
    page.locator('div.container > ul > li.item')
    ```

同时，Playwright 通过对 `locator` 的封装，提供了一系列基于语义的选择器，用于更直观、更稳定、更准确得定位元素（更推荐）：

- `page.get_by_role()`：根据 ARIA 角色定位元素，返回一个 Locator 对象。
- `page.get_by_label()`：根据标签文本定位元素，返回一个 Locator 对象。
- `page.get_by_placeholder()`：根据占位符文本定位元素，返回一个 Locator 对象。
- `page.get_by_text()`：根据文本内容定位元素，返回一个 Locator 对象。

    ```python
    page.get_by_role('button', name='确定')
    page.get_by_text('真实负载调度阈值开关')
    ```

其中 `get_by_role` 最为常用，使用的 ARIA 标签遵从 W3C WAI-ARIA 规范，参考[ARIA in HTML 规范表](https://www.w3.org/TR/html-aria/#docconformance)。与 HTML 标签相比，其分类更注重元素的语义或功能，常用的 ARIA 角色有：

- `button`: 按钮
- `checkbox`: 复选框
- `textbox`: 文本框
- `link`: 链接
- `row`: 表格行
- ...

### 元素操作

Playwright 通过 Locator 对象执行前端页面的交互操作，如点击、输入等，详见 [Playwright Actions 文档](https://playwright.dev/python/docs/next/input)。

> 注意：定位语句可能返回一个或多个 Locator，如果要执行操作，只会对**第一个** Locator 生效。如果返回的是多个 Locator，且需要对全部生效，应当遍历执行操作。

```python
# 定位了5个button
ok_btns = page.get_by_role('button', name='确定')
# 只有第一个被点击
ok_btns.click()
# 通过遍历，每一个都被点击
for ok_btns in ok_btns.all():
    ok_btns.click()
```

### 自动等待

Playwright 提供了自动等待机制，用于确保元素在可见、可用、动画稳定后才会进行相关的操作与断言。这显著减少了开发过程中需要考虑等待元素加载的问题，提高了测试效率。

> 注意：Playwright 默认最大等待时间为30s，可以通过 `set_default_timeout` 方法设置全局超时时间，或在具体操作中添加 `timeout` 参数，设置局部超时时间。

### 断言

针对 Locator、Page 对象，Playwright 提供 expect 及语义化 API 方式进行简洁高效的断言.

```python
expect(page).to_have_url('https://www.example.com')
expect(username_input).to_have_value(re.compile(r'admin*'))
expect(subscribe_checkbox).not_to_be_checked()  # 每个断言都对应的否定版本
expect(banner).to_be_visible()
```

对于其他断言，如正则表达式、字符串、数组等，仍然使用 Python 原生的断言方式。这里建议使用 [`assertpy`](https://github.com/assertpy/assertpy) 三方库，支持通过类似自然语言的API进行断言，且封装了更完善的断言信息与错误消息。

```python
from assertpy import assert_that
assert_that(str_length).is_equal_to(53)
assert_that(title_str).contains('openFuyao')
assert_that(node_lists).is_empty()
```

### 验证鉴权

由于 openFuyao 的前端操作必须登录状态下才能进行，因此需要获取、储存验证信息。由于 openFuyao 管理面的验证信息以 cookie 形式存储在浏览器中。因此，我们可以先进行一次登录操作并保存验证信息，通过 `BrowserContext` 的 `session_storage` 属性提供。后续所有通过此上下文创建的页面，均自带了相关的验证信息，避免反复登录，提升测试效率。

### API请求

通过 `APIRequestContext` 对象可以对 API 进行测试，其参数配置与 `BrowserContext` 基本相同。可以直接从 `BrowserContext` 对象获取 `APIRequestContext` 对象，从而继承相同的上下文配置（如 `base_url`、`storage_state` 等）。

```python
api_context = browser_context.request
resp = api_context.get('https://www.example.com')
```

由于 API 请求上下文在一整个测试中通用，通常建议封装为会话级 fixture，参见 `conftest.py` 中的 `api_context`。

### 事件监听

Playwright 支持添加页面事件的监听，如监听网络请求。

```python
def handle_load(msg):
    print('page is loaded')

page.on("load", handle_load)
```

对于测试某个请求是否发出，或返回是否符合预期，可以使用 Page 对象的 `expect_request` 方法。反之，Playwright 未提供测试请求未发出的方法，推荐使用 `try...except` 进行包装

```python
with page.expect_request('/api/v1/namespaces/default/pods'):
    page.get_by_role('button', name='确定').click()

with page.expect_response(lambda resp: resp.url == '/api/v1/pods' and resp.status == 200 and resp.request.method == 'post') as resp_info:
    page.get_by_text('submit').click()
print(resp_info.value)
```

## Kubernetes for Python

Kubernetes 官方提供了一个 Python 库，提供一系列 K8s 集群访问、资源管理等常用功能。

### Config

`config` 模块是用于加载集群访问配置的入口，可以从本地读取 kubeconfig 文件并建立与 Kubernetes API 的连接。 默认从环境变量 `KUBECONFIG` 中读取，若不存在则读取 `~/.kube/config` 路径

```python
from kubernetes import config

config.load_kube_config("./kubeconfig")
```

### Client

`client` 模块是 Kubernetes 客户端的核心 API 访问层，提供对 K8s 资源的结构化接口以及各类 K8s 资源的数据结构。在 `client` 模块中，各类资源及其相关操作包含在其 groupversion 同名的子包中。先初始化 groupversion API 实例，再调用接口。

```python
from kubernetes import config, client
config.load_kube_config()
# 初始化 core_v1 API 实例后，读取和创建pod
core_v1 = CoreV1Api()
core_v1.read_pod_for_all_namespaces("default", "my-pod")
core_v1.create_namespaced_pod("default", pod_manifest)
# 初始化 apps_v1 API 实例后，列举符合label的deployment
apps_v1 = client.AppsV1Api()
apps_v1.list_namespaced_deployment("default", label_selector="app=nginx")
```

### Dynamic

可以通过 `dynamic` 模块来获取 CRD。

```python
from kubernetes import config, dynamic
from kubernetes.client import api_client

config.load_kube_config()
dyn_client = dynamic.DynamicClient(api_client.ApiClient())
v1_myresources = dyn_client.resources.get(api_version="my.example.com/v1", kind="MyResource")
```

### Watch

`watch` 模块允许实时监听资源变化

```python
from kubernetes import config, watch

config.load_kube_config()

w = watch.Watch()
for event in w.stream(core_v1.list_pod_for_all_namespaces):
    print("Pod event")
```

### Stream

`stream` 模块允许在 Pod 中执行命令

```python
from kubernetes import config, client, stream

config.load_kube_config()
core_v1 = client.CoreV1Api()

resp = stream.stream(core_v1.connect_get_namespaced_pod_exec,
    "my-pod", "default",
    command=["sh", "-c", "ls /"],
    stderr=True,
    stdin=False,
    stdout=True,
    tty=False,
)
```

## 开发流程

参考在离线混部（colocation）相关文件，逐步搭建特性的自动化集成测试模块

1. 在 `testcases/functional/integration` 下创建新的目录，从 `colocation` 目录中复制 `conftest.py` 到新目录;
2. 创建一个 `test_xxx.py` 作为测试文件，建议按照测试发生的页面对用例进行文件分组。
3. 编写测试用例代码：
    - 根据运行测试所在的页面，编写对应的页面 fixture
    - 根据测试用例的逻辑关系分组，组织一个或多个测试类
    - 编写测试函数代码。操作紧密相关的多个用例建议整合为一个函数，减少重复代码的同时，避免反复创建测试上下文，提升运行效率。

### 辅助工具

#### CLI 工具

使用 Playwright 命令行工具，打开浏览器窗口与 Playwright 调试器，支持以下功能：

- 操作录制：直接在页面操作，即时生成相应的测试代码。需要在语言选择栏将语言切换为 Python - Pytest。
- 快速定位：直接点击页面上的元素，快速生成建议的 locator 定位语句。
- Locator 调试：输入 locator 语句，在当前页面上查看定位结果，方便调试。

```bash
playwright open <url>       # 默认关闭录制
playwright codegen <url>    # 默认启用录制
```

#### Chrome 扩展

在 Chrome 应用商店安装扩展 [Playwright CRX](https://chromewebstore.google.com/detail/playwright-crx/jambeljnbnfbkcpnoiaedcabbgmnnlcd)。在 Chrome 中打开任意页面，点击地址栏右侧的扩展图标，即可进入 Playwright 调试模式。扩展的 UI 及功能与上述 CLI 工具相同。

## 运行测试

### 环境准备

参见 e2e-auto-test [Readme相关章节](../README.md#环境变量配置)

### VSCode 测试工具（推荐）

打开VSCode左侧测试标签，选择 pytest 项目，设置测试目录为 `testcases`，即可自动识别目录下的所有测试用例，并以树形结构展示。如果想要只显示特定测试用例，可在 `.vscode/settings.json` 文件中修改 `python.testing.pytestArgs` 字段为指定的目录或文件。

可以在侧边栏中运行、调试全部用例或特定文件、测试类与测试函数。

测试完成后，会在侧边栏与输出终端打印测试结果，可在 UI 上快速跳转查看，且测试结果将被缓存。

### 命令行运行

进入当前目录，直接运行 pytest 命令

```bash
pytest  # 运行当前目录下全部测试
pytest <directory>  # 运行指定目录下全部测试

pytest <path_to_test_file>  # 运行特定测试文件
pytest <path_to_test_file>::<test_class>  # 运行特定测试类
pytest <path_to_test_file>::<test_class>::<test_method>  # 运行特定测试函数
```

### 运行配置

1. 无头/有头浏览器

    通过命令行 `pytest` 启动测试，或在VSCode 测试工具点击*运行*，将默认使用无头浏览器，此时浏览器在后台运行，不显示窗口，运行更快。若需要有头浏览器将测试过程可视化，可添加相关参数选项。

    | 途径 | 配置方法 |
    | --- | --- |
    | 命令行参数选项 | 浏览器默认以无头模式启动，添加 `--headed` 启用有头模式 |
    | <mcfile name="pytest.ini" path="pytest.ini"></mcfile> | 通过 `addopts` 添加 `--headed`，参见 <mcfile name="pytest.ini" path="pytest.ini"></mcfile> 文件内示例 |
    | VSCode 测试工具 | 点击**运行**则依照 `pytest.ini` 配置，点击**调试**强制启用有头模式 |

2. Tracer

    已开启 Playwright Tracer 以可视化形式跟踪测试过程，包括页面截图、网络请求、DOM 操作等。与无头/有头切换一样，可以通过命令行参数选项或 `pytest.ini` 配置。

    | 参数 | 说明 |
    | --- | --- |
    | `off` | 不记录 trace (默认) |
    | `on` | 记录每一个测试的 trace |
    | `retain-on-failure` | 仅在测试失败时记录 Trace |
  
    测试运行结束后，将在 `test-results/` 路径下、与测试函数同名的文件夹中创建 trace.zip 文件。使用 `playwright show-trace <trace_file>` 打开本地 GUI 查看测试记录。

3. 添加环境变量 `PWDBUG` 为 1， 能以GUI调试器启动测试。支持自动执行、逐行执行。如，在 powershell 中

    ```powershell
    $env:PWDEBUG=1
    pytest 
    ```
