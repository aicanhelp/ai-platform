# openFuyao v26.09 昇腾推理服务与 KV 共享特性测试报告

> Author: 灵雀云

## 1. 背景说明

openFuyao AI 推理体系（InferNex，sig-ai-inference）在昇腾环境提供以 vLLM-Ascend 为推理引擎、KServe LLMInferenceService 为编排的模型部署服务，并通过 Mooncake 分布式 KVCache 池化存储提供跨 rank KV 共享（KV-aware）链路，用于提升长上下文多轮会话场景的前缀复用率与吞吐。

灵雀云作为社区协同测试伙伴，在 v26.09 版本周期内（2026-09-01 — 2026-09-21），在昇腾 910B 环境完成 **5 个模型的部署与容量实测**（Qwen3-30B-A3B、Qwen3.5-397B-A17B、MiniMax-M2.7、GLM-5.2、DeepSeek-V4-Flash）与 **1 个 PD 分离硬件形态仿真对照**（GLM-5.3），重点验证各模型的可用并发与关键性能差异；其中 DeepSeek-V4-Flash 采用 openFuyao KV 共享链路完成 A/B 对照，作为本轮 **openFuyao KV-aware 相关链路的验证**，实测吞吐提升 24%~67%、TTFT 降低 24%~44%，1,440 个请求全部成功、0 错误。

### 1.1 特性清单

## 2. Goals（目标）

- 验证昇腾环境下 5 个模型（Qwen3-30B-A3B、Qwen3.5-397B-A17B、MiniMax-M2.7、GLM-5.2、DeepSeek-V4-Flash）的部署拓扑与各场景可用并发容量；
- 验证 openFuyao KV 共享链路（Mooncake 跨 rank KV 共享）在长上下文多轮 agent 负载下的性能收益与稳定性；
- 识别各模型容量边界与关键性能差异（长上下文限制、投机解码收益等），形成容量规划依据；
- 通过 GLM-5.3 PD 分离仿真对照 A2 / A3 硬件形态，为后续实卡验证提供参考；

## 3. Non-Goals（非目标）

- 本轮结果用于容量规划与配置比较，不作为生产 SLO 承诺
- 跨模型数据因模型、上下文长度、投机解码配置与卡数不同，不构成严格横向比较
- 不覆盖多实例路由与多副本弹性伸缩（KV 共享对照为单服务、双 DP rank）
- 不单独拆分 KV-aware 路由器与共享池的独立贡献
- GLM-5.3 PD 分离为仿真数据（未上卡），不用于生产 SLO 或部署承诺
- Qwen3-30B-A3B 本轮仅验证 chat，未覆盖 coding 与 rag
- 不涉及安全专项测试与 7×24 长稳测试（以性能与容量验证为主）

## 7. 测试结论

### 7.1 整体结论

本次协同测试在昇腾 910B 环境（8 卡 910B4 / 16 卡 910B3 Atlas 800 A2）完成 5 个模型实测 + 1 个 PD 分离仿真，共计 12 项验证：**11 项实测全部通过**（含 1 项容量边界确认），仿真 1 项仅作参考；未发现产品缺陷，发现的 4 项事项均为测试覆盖范围限制与后续验证建议（见 6.4，已转化为 7.4 / 7.5 后续测试建议），无遗留问题。

- **openFuyao KV 共享链路验证有效（核心结论）**：DeepSeek-V4-Flash 在 16 卡、17.5K 长上下文多轮 agent 负载下，Mooncake 跨 rank KV 共享相对 graph + prefix cache 基线，三档（8/16/32 会话）吞吐提升 24%/51%/67%，TTFT 降低 24%/44%/40%，有效前缀复用率由 41.3% 提升至 84.4%；三档共 1,440 个请求全部成功、0 错误，无引擎重启或乱码。完整优化链路相对无 KV 的 eager 基线，并发 32 时吞吐达 4.8 倍（48.1 → 230.9 tok/s），TTFT 由 10.2 s 降至 1.9 s。
- **长上下文是容量的主要限制**：Qwen3.5-397B 16 卡可覆盖 rag 目标窗口（163,840），8 卡窗口不足时 rag 请求 24.0% 超窗、coding 16 会话 KV 峰值 85.6%；部署容量首先由模型权重与 KV 需求决定，容量规划应先看单会话上下文长度，再看场景名称。
- **各模型容量结论**：Qwen3-30B-A3B 8 卡 chat c6 档 274/274 请求成功（E2E p90 6.87 s、输出吞吐 103.1 token/s）；MiniMax-M2.7 chat 可用并发高于 32、rag 以 4 会话为稳妥工作点；GLM-5.2 32 会话 ITL 96.7 ms 仍未显存饱和，投机解码每步生成 3.31~3.35 个 token（MTP 接受率 76.9%~78.3%）。
- **待补范围**：多实例路由、弹性伸缩及 KV 共享在其他模型上的收益仍需单独验证；GLM-5.3 PD 分离需实卡验证。

### 7.2 约束说明

- 本轮结果用于容量规划和配置比较，不作为生产 SLO 承诺
- 跨模型数据因模型、上下文长度、投机解码配置和卡数不同，不构成严格横向比较
- 环境 B（双节点 910B3）TP 组需落在单节点内，跨节点使用 DP / EP
- KV 共享对照为单服务、双 DP rank，未覆盖多副本弹性伸缩；未拆分 KV-aware 路由器与共享池的独立贡献
- GLM-5.3 PD 分离数据为仿真，不能用于生产 SLO 或部署承诺
- Qwen3-30B-A3B 本轮仅验证 chat（最大上下文 40,960），未覆盖 coding / rag

### 7.3 风险提示

1. **中风险**：KV 共享链路的收益结论基于单服务、双 DP rank 对照，多副本 / 弹性伸缩生产形态下的收益与稳定性未验证（问题 1），外推需谨慎
2. **低风险**：8 卡长上下文（160K 级 rag）存在 24.0% 超窗与 KV 85.6% 的容量风险，选型不当会造成请求失败率上升（问题 2）；Qwen3-30B-A3B 仅覆盖 chat，容量画像不完整；GLM-5.3 PD 分离仿真显示 A3 服务端 TTFT +37.3%，实卡形态未验证（问题 4）

### 7.4 改进建议

1. **KV 共享链路**：补充多副本 / 弹性伸缩 / 多实例路由场景的 A/B 验证；拆分 KV-aware 路由器与共享池的独立贡献；扩展 KV 共享在其他模型（长上下文 rag / coding 场景）上的收益验证
2. **容量规划指引**：发布"模型 × 卡数 × 上下文长度"选型建议（如 160K 级 rag 使用 16 卡），并强调先看单会话上下文长度、再看场景名称
3. **配置闸门文档化**：GLM-5.2 等模型的图捕获与准入配置对容量上限的影响纳入文档与容量评估方法
4. **PD 分离实卡验证**：GLM-5.3 PD 分离在 A2 / A3 对应规模实卡上验证，重点复核服务端 TTFT 劣化（仿真 +37.3%）

### 7.5 后续测试建议

- 在多副本、弹性伸缩与多实例路由形态下复验 openFuyao KV 共享链路收益
- 补充 Qwen3-30B-A3B 的 coding / rag 场景容量验证
- 开展 GLM-5.3 PD 分离实卡验证（A2 / A3 对照）
- 将本轮容量边界结论（8 卡 / 16 卡选型）沉淀为部署模板或默认配置建议
