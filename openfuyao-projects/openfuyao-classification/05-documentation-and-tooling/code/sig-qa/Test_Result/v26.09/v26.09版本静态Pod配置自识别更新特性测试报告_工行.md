# openFuyao v26.09 静态Pod配置自识别更新（OFEP0037）特性测试报告

> Author: 工行

## 1. 背景说明

静态 Pod（kube-apiserver、kube-controller-manager、kube-scheduler、etcd）是 Kubernetes 控制面的核心承载组件。openFuyao v26.09 安装部署特性引入静态 Pod 配置自识别更新（OFEP0037）能力：用户修改 BKECluster（bc）配置参数并重新 apply 后，系统自动识别发生变化的静态 Pod 组件配置，通过 `EnsureMasterConfigUpdate` / `EnsureEtcdConfigUpdate` 两个 phase 编排下发，仅更新受影响组件的 manifest 与静态 Pod 参数，实现组件级独立、幂等、受防护（不可变字段 webhook 拦截）的配置热更新。

工行作为社区协同测试伙伴，在 v26.09 版本周期内，基于"管理集群搭建业务集群后，修改相应组件的配置参数，再重新 apply"的方式，对 OFEP0037 特性开展了用例自验证。

### 1.1 特性清单

| ofep编号 | [组件名称]特性名称 | sig组 | 特性描述 |
| -------- | ------------------ | ----- | -------- |
| OFEP0037 | [安装部署]静态Pod配置自识别更新（安装部署静态pod更新） | sig-installation | 修改 BKECluster（bc）配置后自动识别并更新对应控制面静态 Pod（kube-apiserver / kube-controller-manager / kube-scheduler / etcd）配置：通过 EnsureMasterConfigUpdate / EnsureEtcdConfigUpdate phase 编排，支持组件级独立更新与解耦、hash 比对、幂等更新（相同配置不触发）、不可变字段 webhook 拦截、非静态 Pod 配置变更不误触发 |

## 2. Goals（目标）

- 验证业务集群控制面三个静态 Pod 组件（apiserver / controllerManager / scheduler）配置的按组件独立更新，及同时修改多组件时的单次更新流程；
- 验证 etcd 静态 Pod 配置更新与控制面配置更新的解耦，以及两类配置同时修改时双 phase 的触发与执行顺序；
- 验证配置更新幂等性（apply 相同配置不触发更新）与非静态 Pod 配置（Kubelet / 仓库 / Labels 等）变更不误触发更新；
- 验证 etcd 不可变字段（DataDir / ServerCertSANs / PeerCertSANs）的 webhook 拦截防护；
- 验证管理集群管控面配置自更新能力；

## 3. Non-Goals（非目标）

- 不涉及 kubelet / containerd 等非静态 Pod 组件配置更新效果本身的验证（仅验证其变更不触发静态 Pod 更新）
- 不涉及异常场景（更新失败回滚、节点故障、超时恢复等）验证
- 不涉及性能测试、长稳测试、安全专项测试与资料测试
- 不涉及多架构（x86/arm）、高可用多控制面节点场景覆盖（单套环境验证）

2. **管控面静态 Pod 的配置更新与 etcd 更新解耦**（结合场景二验证）。

### 5.4 场景四：管理集群管控面配置自更新

#### 5.4.1 场景描述

在管理集群上修改其自身 bc 的控制面组件参数（apiServer / controllerManager / scheduler），验证管控面配置自更新能力：对应 k8s 组件完成更新、Pod 重启，参数未变化的其余组件不更新、Pod 不重启。

**已知前提**：引导节点向管理集群传递 bc 时存在参数丢失（详见问题 1 / [issue #224](https://gitcode.com/openFuyao/cluster-api-provider-bke/issues/224)），因此测试时修改的参数不能与管理集群上 bc 的现有参数相同，需取不同值才能观察到更新效果。

#### 5.4.3 用例详情

---

**功能_013：管理集群管控面配置自更新** | P0 | 功能测试 | **通过**

- **前置条件：**
  1. 管理集群正常运行，已获取管理集群 bc 修改前的组件 hash（注意该 hash 仅针对管理集群上的 bc）

- **步骤描述：**

  3. 修改 scheduler 的 kube-api-qps（"1000" → "2000"）并 apply，观察更新情况

  1. 触发 EnsureMasterConfigUpdate phase，修改相应参数后对应 k8s 组件完成更新、Pod 重启；参数未变化的其余组件不更新、Pod 未重启
- **实测结果：** 通过——分别修改 apiServer / controllerManager / scheduler 参数后，对应组件 hash 值发生变化，对应 k8s 组件完成更新、Pod 重启；参数未变化的其余组件未更新、Pod 未重启

## 7. 测试结论

### 7.1 整体结论

本次协同测试基于工行 OFEP0037 用例自验证记录，覆盖**业务集群控制面静态 Pod 配置更新**（4 个用例）、**etcd 静态 Pod 配置更新与解耦**（2 个用例）、**配置更新幂等性与误更新防护**（5 个用例）和**管理集群管控面配置自更新**（1 个用例），共计 **12 个功能用例，全部通过（100%）**，关联已知问题 1 个（主要，issue #224，评审允许遗留）；另提交 issue #225（主要，无效参数导致静态 Pod 更新后无法启动，已关闭，不计入遗留问题）。

核心能力验证结论：

1. **组件级独立更新**：修改 apiServer / controllerManager / scheduler 任一组件 extraArgs，仅该组件 hash 变化、manifest 更新、静态 Pod 参数生效，其余组件不受影响；三个控制面静态 Pod 组件配置更新相互独立、解耦；
2. **与 etcd 解耦且有序**：修改 etcd 配置仅触发 EnsureEtcdConfigUpdate；控制面与 etcd 配置同时修改时双 phase 均触发，按"先 etcd、后控制面"顺序执行；
3. **多组件同次更新**：同时修改多个控制面组件配置可在一轮更新流程中完成；
4. **幂等性**：apply 相同配置不触发任何更新 phase，manifest 与 Pod 均无变化；
5. **不可变字段防护**：etcd DataDir / ServerCertSANs / PeerCertSANs 修改被 webhook 有效拦截并返回提示词，不触发更新；
6. **无误触发**：修改 Kubelet / 仓库 / Labels 等非静态 Pod 配置不会误触发静态 Pod 配置更新；
7. **管理集群自更新**：管理集群管控面组件配置自更新可用，参数变化组件更新重启、未变化组件不受影响（受 issue #224 约束，修改参数需与管理集群 bc 现有参数不同）。

### 7.2 约束说明

- 引导节点向管理集群传递 bc 时存在参数丢失（issue #224）：管理集群自更新场景下，修改参数不能与管理集群 bc 现有参数相同，需取不同值；若配置了丢失的参数会导致集群一直处于更新状态，需重新编辑 bc 恢复
- etcd 组件配置更新可能引起 kube-controller-manager、kube-scheduler 的 Pod 重启（配置不会更新），属预期行为，业务侧需感知该重启窗口
- 本轮验证方式为"管理集群搭建业务集群后，修改相应组件配置参数，再重新 apply"，未覆盖更新失败/超时等异常场景

### 7.3 风险提示

1. **中风险**：issue #224（bc 参数传递丢失）影响管理集群 bc 配置自更新能力，已有规避措施并经社区评审允许遗留，建议后续版本修复
2. **低风险**：etcd 配置更新会连带引起控制面部分 Pod 重启，多组件频繁变更时存在短暂的控制面抖动窗口，建议在变更窗口期执行

### 7.4 改进建议

1. 修复引导节点向管理集群传递 bc 时的参数丢失问题（issue #224）
2. 文档补充说明：etcd 配置更新可能引起 kube-controller-manager / kube-scheduler Pod 重启的预期行为；管理集群自更新的参数取值注意事项
3. 原始用例编号 004~007、010、014~017 未包含在本自验证记录中，建议补齐相应场景（如异常场景、字段级边界）的验证记录

- 补充异常场景验证：配置更新失败/超时的回滚与恢复、更新过程中节点故障
