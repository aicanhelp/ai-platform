# openFuyao v26.09 安装部署 & NPU 特性测试报告

> Author: 博云

## 1. 背景说明

openFuyao 是面向云原生 AI 场景的开源容器平台，提供从集群安装部署、NPU 异构算力管理到 AI 推理服务 Hosting 的端到端能力。博云作为社区协同测试伙伴，在 v26.09 版本周期内，基于自有昇腾 ARM 环境（Kylin V10 aarch64 + Ascend 310P3 × 2）开展了安装部署与 NPU 相关特性的协同测试。

本次测试聚焦以下三个方向：

- **引导节点与业务集群安装部署**：基于 bke 在线方式初始化引导节点、部署管理面，并完成业务集群（单 master 共部署节点）安装；
- **NPU 组件安装部署**：通过管理面应用市场安装 npu-operator 26.9.0-rc.1（含 volcano 批调度组件），验证组件下发、镜像拉取与运行状态；
- **NPU DRA 软切分调度**：基于 npu-dra-plugin 验证 DRA（Dynamic Resource Allocation，动态资源分配）软切分（vnpuMode: soft）场景下的 vNPU 资源上报、算力/内存配额申请、多 vNPU 共卡、满算力分配与 CEL 设备选择器等能力。

测试基础平台为 openFuyao 26.6.0 业务集群（K8s v1.34.3-of.1），被测 v26.09 对象包括 npu-operator 26.9.0-rc.1 与 npu-dra-plugin（main 分支 / helm chart 1.0.0）。引导节点安装部署问题在基础平台环境搭建过程中发现，经独立环境复验，属"宿主机环境（FORWARD 链默认 DROP）触发 + bke 安装器未适配"的兼容性缺陷而非任意环境必现的产品缺陷（详见 5.1.4 问题 1），建议随 v26.09 版本一并修复与复验。

#### 5.1.4 关键问题分析

**问题 1：引导节点管理面（30010 端口）外部无法访问（已复验无问题）**

- **现象**：`bke init` 成功、集群内 Pod 全部 Running、本机访问 303 正常，但来自节点外部的新连接被静默丢弃（tcpdump 抓包仅见 SYN 重传、无 SYN-ACK）。
- **根因（双因素叠加，缺一不可）**：
  - **产品侧（未适配）**：宿主机 nerdctl 默认网桥 CNI 配置（`/etc/cni/net.d/nerdctl-bridge.conflist`）由 `bke init` 生成，启用 firewall 插件且 `ingressPolicy: same-bridge`。该插件只做网桥间隔离（CNI-ISOLATION-STAGE-1/2）与既有连接放行——`CNI-FORWARD` 链仅含每容器 IP 的 ESTABLISHED 入向与源地址出向放行规则、无兜底 DROP——不为外部新建（NEW）流量生成放行规则。
  - **环境侧（触发条件，决定性）**：博云宿主机 iptables filter 表 FORWARD 链默认策略为 DROP。外部 NEW 状态入站流量经 DNAT 后进入 FORWARD 链，不匹配任何放行规则，命中默认 DROP 被静默丢弃；FORWARD 默认策略为 ACCEPT 的宿主机上，未匹配规则的流量落回 ACCEPT 策略正常转发，不受影响。
- **影响范围**：在触发条件下（宿主机 FORWARD 链默认 DROP），nerdctl0 网桥上所有容器的 hostPort 外部访问均被阻断，包括管理面 30010、k3s API 36443、本地镜像仓库 40443、Yum 仓库 40080、Chart 仓库 38080——不规避时不仅管理面打不开，业务集群安装也会因节点无法访问引导节点仓库而失败。
- **复现性与独立复验**：博云宿主机（FORWARD 默认 DROP）100% 可复现；2026-09-03 重装复现验证确认 `bke init` 每次重装都会重新生成含 `same-bridge` 的 CNI 配置，且容器 IP 会漂移（如 10.4.0.14 → 10.4.0.6）。2026-10 于干净虚拟机宿主机（FORWARD 默认 ACCEPT）独立复验：`bke init` 后 conflist 同样含 `same-bridge`，但 `-P FORWARD ACCEPT`、`CNI-FORWARD` 链无兜底 DROP，外部 Windows 机器可正常连接 30010——证实 `same-bridge` 单独存在并不阻断外部访问。综上，该问题定性为"宿主机环境（FORWARD 默认 DROP）触发 + bke 未适配"的兼容性缺陷，而非任意环境必现的纯产品缺陷；FORWARD 默认 DROP 属合法且常见的宿主机状态（装过/在跑 Docker、启用 firewalld 或执行安全加固的节点均如此），安装器不应假设其一定为 ACCEPT。
- **规避措施（已在测试环境验证）**：向 `CNI-FORWARD` 链插入外部入站放行规则；因重装后容器 IP 漂移，采用动态解析容器 IP 的修复脚本（`/usr/local/sbin/bke-fix-forward.sh`，含就绪重试与幂等检查）+ `rc.local` 开机自启持久化。修复后 `Test-NetConnection 30010 → True`，业务集群安装顺利推进；FORWARD 默认为 ACCEPT 的干净宿主机无需任何规避。
- **修复建议**：① `bke init` 检测宿主机 FORWARD 链默认策略，为 DROP 时自动插入上述端口的放行规则或调整 `same-bridge` 策略（兼容容器 IP 漂移，动态解析而非固定 IP）；② `bke init` 收尾增加管理面端口外部可达性自检，杜绝"初始化成功但外部不可达"的假成功；③ 至少在安装文档"前提条件/FAQ"中明确说明该已知问题与规避方法。

#### 5.2.4 关键问题分析

**问题 2：volcano 组件 CrashLoopBackOff——镜像二进制属主权限与 securityContext drop ALL 冲突（主要）【已在 v26.09-rc.2 版本修复，根因：values.yaml 中 mindcluster 安装参数配置错误】**

- **现象**：volcano-scheduler / volcano-controllers 持续 CrashLoopBackOff，报 `Permission denied`；镜像拉取、调度、网络均正常。
- **根因**（实测取证）：
  1. **镜像缺陷**：MindX 定制镜像内二进制属主为 `hwMindX:hwMindX`、权限位 `0500`（`-r-x------ 1 hwMindX hwMindX vc-scheduler`），仅属主可读执行；
  2. **部署清单缺陷**：Deployment 配置 `runAsUser: 0` + `capabilities.drop: [ALL]`，root 的 `CAP_DAC_OVERRIDE` 被丢弃，容器 uid=0 ≠ 属主 hwMindX，执行二进制时触发 DAC 拒绝；
  3. **附带缺陷**：`init-permission` 初始化容器脚本依赖 `sudo`，而 busybox 基础镜像内无 sudo，权限修复从未发生；且 init 容器修改的是自身镜像层文件，对主容器镜像层无跨层生效能力。
- **影响范围**：volcano 调度器不可用，影响批调度/任务调度功能，npu-operator 26.9.0-rc.1 组件链路不完整。
- **规避措施（建议方案，未在环境执行）**：保留 `DAC_OVERRIDE` capability（`capabilities: drop: ["ALL"], add: ["DAC_OVERRIDE"]`）；或以镜像属主用户运行（`runAsUser: 2000`）；或替换为 `0755` root 属主镜像。
- **修复建议**：
  1. 镜像侧（治本）：重新构建 volcano 镜像，将二进制权限改为 `0755`、属主 root:root，与 `runAsUser: 0` + `drop ALL` 安全基线兼容；
  2. 部署清单侧：bke/应用市场下发的 volcano Chart 校验 securityContext 与镜像二进制权限兼容性，或在保留 drop ALL 前提下追加 `DAC_OVERRIDE`；
  3. init 容器修复：脚本移除 sudo 依赖，并重新评估"init 容器修改主容器镜像层权限"的设计（可改为启动命令先 chmod 后 exec，或镜像构建期固化权限）；
  4. 文档/FAQ 补充 MindX 定制镜像与 securityContext 的兼容性说明。

#### 5.3.4 关键问题分析

**说明**：已于 QA 例会中联系开发澄清——本次测试所用 DRA 版本有误，该版本软切分能力尚未完善，问题 3/问题 4 的实测表现系测试版本能力所限；相关问题均已解决，无遗留问题。

**问题 3：DRA 软切分场景下 coreCapacity=100% 满算力请求调度失败，调度器不尝试第二张物理卡（主要）**

- **现象**：软切分场景下，同节点任何一张卡已有其他 vNPU 分配时，`coreCapacity=100`（等于设备 capacity max 值）的请求必然 Pending，调度事件报 `cannot allocate all claims`（无 per-device 细节）。
- **实验矩阵（控制变量法）**：

| # | 请求规格 | 附加操作 | 结果 | 分配位置 |
|---|---------|---------|------|---------|
| 1 | 10Gi / 100% | 无 | Pending | — |
| 2 | 10Gi / 100% | CEL 选择器强制 `physicalID != 0` | Pending | — |
| 3 | 10Gi / 50% | 无 | Running | npu-0（与 demo1 同卡，未选空闲 npu-1） |

- **根因判定（两层因素叠加）**：
  1. **直接原因**：`coreCapacity=100` 的请求无法与任何已有分配共存，且即便目标设备完全空闲（实验 2），分配也失败——推测 100% 在 capacity 记账语义中被当作"独占整卡"处理，与 `allowMultipleAllocations: true` + `shareCount` 的软切分语义冲突，走了不兼容分支；
  2. **放大因素**：分配器对多设备不做容量寻优（实验 3），第一张卡有残留分配时 100% 请求必然失败，无法通过自然的换卡规避；
  3. scheduler 启动日志存在 `component has alpha features enabled in emulated version, this is unsupported: features=[DRAConsumableCapacity]` 告警，openFuyao v1.34.3 的组件兼容层将此门控识别为"模拟版本中的 alpha 特性、不支持"，capacity 相关的完整分配路径可能未真正生效或存在缺陷。
- **影响范围**：所有软切分场景下申请满算力 vNPU（coreCapacity=100）的 Pod；不影响 `coreCapacity < 100` 的任意组合（单卡总和 ≤100）及整卡模式（full）、硬切分。
- **规避措施（已验证有效）**：软切分按"单卡总算力 100% 预算"规划（如 30%+50% 组合共存）；满算力需求改用整卡模式（对应卡 `vnpuMode` 改为 full），或先确保目标卡无其他分配再提交 100% 请求；CEL 选择器不能规避本问题。
- **修复建议**：
  1. 上游排查 v1.34.3-of.1 对 `DRAConsumableCapacity` 的 emulated-version 兼容层，确认 capacity 记账路径完整启用；
  2. DRA ResourceSlice 分配器增加多设备容量寻优（首个候选设备容量不足时继续尝试后续设备）；
  3. 明确 `coreCapacity=100` 与 `allowMultipleAllocations=true` 的组合语义；
  4. npu-dra-plugin 文档注明当前限制，或驱动侧对 `coreCapacity=max` 请求自动降级处理。

---

**问题 4：软切分任务容器内 npu-smi info 仍显示整卡资源（次要）**

- **现象**：软切分任务发布后，进入容器执行 `npu-smi info` 看到的还是整卡资源。
- **影响**：用户无法在容器内直观确认 vNPU 配额生效情况，易对软切分是否生效产生困惑（实际配额经 `/etc/enpu/vcann-rt/npu_info.config` 已生效）。

## 7. 测试结论

### 7.1 整体结论

本次协同测试覆盖**引导节点与管理面安装部署**（4 个用例）、**NPU 组件安装部署**（2 个用例）和 **NPU DRA 软切分调度**（8 个用例），共计 **14 个测试用例**：通过 7 个、部分通过 1 个、不通过 6 个，发现问题 4 个（主要 3、次要 1）。

- **基础安装部署流程基本可用**：`bke init` 在线初始化、管理面本机访问、业务集群安装均正常；但宿主机 FORWARD 链默认 DROP 的环境下引导节点管理面外部访问不可达（问题 1，"环境触发 + 产品未适配"的兼容性缺陷：该宿主机 100% 可复现，FORWARD 为 ACCEPT 的干净宿主机经 2026-10 独立复验不受影响），不规避时将阻塞业务集群安装，已在测试环境通过动态放行脚本规避并验证；该问题现已解决。
- **NPU 组件安装链路存在阻塞缺陷**：npu-operator 26.9.0-rc.1 安装下发、镜像拉取、调度正常，但其携带的 volcano 批调度组件因镜像二进制属主权限与 securityContext drop ALL 冲突 100% 崩溃（问题 2），批调度能力不可用；该问题已在 v26.09-rc.2 版本修复（根因：values.yaml 中 mindcluster 安装参数配置错误）。
- **DRA 软切分基础能力可用，满算力场景受限系测试版本能力未完善**：特性门控开启、ResourceSlice 资源上报、非满算力 vNPU 分配与多 vNPU 同卡共存（30%+50%）均正常；满算力（coreCapacity=100%）请求在同节点存在任何残留分配时必然 Pending，且分配器不做跨卡寻优（问题 3）。经 QA 例会联系开发澄清：本次测试所用 DRA 版本有误、该版本软切分能力尚未完善，上述表现系测试版本能力所限，相关问题均已解决。
- 测试发现的 5 个问题均已有解决，无遗留问题（问题 2 已在 v26.09-rc.2 版本修复；问题 3/4 经 QA 例会澄清系测试所用 DRA 版本有误、该版本软切分能力未完善所致）；建议在修复/完善版本上完成回归验证。

### 7.2 约束说明

- 测试环境 OS 为 Kylin V10 (Lance) aarch64，**不在 openFuyao 官方支持列表**，相关结论基于非官方支持环境，建议在官方支持 OS 上复验
- `DRAConsumableCapacity` 特性门控本集群默认未开启，需同时为 kube-apiserver 与 kube-scheduler 手工开启，否则容量请求被 apiserver 静默丢弃（软切分配额完全不生效）
- 静态 Pod manifests 目录严禁存放 `.bak` 等备份文件（kubelet 解析目录下所有文件，旧定义与主 manifest 冲突且旧定义胜出）；修改后应通过 `pgrep` + `/proc/<pid>/cmdline` 验证进程实际参数
- 软切分场景满算力（100%）vNPU 受问题 3 限制：需按"单卡总算力 100% 预算"规划组合，或满算力需求改用整卡模式；CEL 选择器无法规避（该限制系测试版本能力所限，已经 QA 例会澄清，见 5.3.4 说明）
- 引导节点 nerdctl 容器（k3s、本地仓库）重装后 IP 会漂移，基于固定 IP 的防火墙/放行配置将失效

### 7.3 风险提示

1. **高风险**：问题 1（管理面外部不可达）影响 FORWARD 链默认 DROP 宿主机（常见于装过/在跑 Docker、启用 firewalld 或执行安全加固的节点）上新装环境的安装可用性，且失败模式为静默丢包而 `bke init` 仍报成功，未获知规避方法时业务集群安装被完全阻塞，建议正式发布前修复或在文档中显著说明——该问题已解决
2. **高风险**：问题 2（volcano 崩溃）导致 v26.09 npu-operator 组件链路不完整，批调度/任务调度能力不可用，需在发布前修复镜像权限或部署清单——已在 v26.09-rc.2 版本修复
3. **中风险**：问题 3（DRA 满算力调度失败）影响软切分满算力场景，有明确规避方案；同时暴露 `DRAConsumableCapacity` 在 v1.34.3-of.1 兼容层下的 alpha 告警，建议排查确认容量记账路径完整生效——经 QA 例会澄清系测试 DRA 版本有误所致，已解决

### 7.4 改进建议

1. **bke 安装器**：`bke init` 检测宿主机 FORWARD 链默认策略，为 DROP 时自动插入 30010/36443/40443/40080/38080 端口放行规则或调整 nerdctl CNI `same-bridge` 策略（兼容容器 IP 漂移），并在收尾增加管理面端口外部可达性自检
2. **bke 运维安全**：`bke reset --all --mount` 高危操作增加二次确认
3. **volcano 镜像与部署清单**：镜像二进制改为 `0755` root 属主；Chart 校验 securityContext 与镜像权限兼容性；修复 init 容器 sudo 依赖与跨层修改设计
4. **DRA 调度**：排查 `DRAConsumableCapacity` emulated-version 兼容层；分配器增加多设备容量寻优；明确 `coreCapacity=100` 与 `allowMultipleAllocations=true` 的组合语义
5. **文档**：补充 Kylin V10 支持状态说明、静态 Pod manifests 目录管理注意事项（禁止备份文件混放）、软切分当前限制与规避方案、容器内 vNPU 配额查看方式、MindX 定制镜像与 securityContext 兼容性说明

### 7.5 后续测试建议

- 问题 1/2/3 已修复/澄清，建议在相同环境（Kylin V10 aarch64 + Ascend 310P3 × 2）回归验证，重点覆盖重装场景（CNI 配置重生成、容器 IP 漂移），其中问题 3 需以正确的 DRA 版本复测软切分满算力与跨卡寻优；问题 1 回归需构造 FORWARD 默认 DROP 宿主机（可用 `iptables -P FORWARD DROP` 模拟）验证放行逻辑生效，并确认 FORWARD 为 ACCEPT 的环境不引入回归；建议在博云宿主机补查 FORWARD 默认 DROP 的来源（`iptables -S FORWARD | head -1`、`iptables -S | grep -i docker`、`systemctl is-active docker firewalld`），闭环根因链
- 补充整卡模式（full）、硬切分场景对照验证
- 在官方支持 OS（openEuler 22.03/24.03 等）环境复验安装部署与 DRA 软切分结论
- 扩展多节点、多卡（>2）规模下的 DRA 调度验证（跨节点寻优、碎片整理）
