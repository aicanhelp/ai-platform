# openFuyao日志建议性规范V0.1

## 1.总体概述
本规范为openFuyao社区的日志规范，主旨是通过一些原则和具体的实施规范，确保日志信息完整、分级合理，最终目标是让用户能够通过日志清楚地了解问题、准确地上报问题；让开发人员能够快速地定位问题、高效地解决问题。  
本规范为一般性的项目日志记录规范，部分特殊日志，如安全日志、审计日志等，可根据具体情况提出更加具体和详细的要求。  
由于社区中各个项目情况不同，本规范仅作为建议性规范，各项目可根据情况对规范进行适当增减形成自己的规范。

## 2 日志格式规范
基于当前社区项目使用语言不同，部分历史代码已有日志选型的特征，本节仅对日志中应当具有的特征进行描述，不限定具体日志框架。对于日志的内容要求如下：
- 日志中必须包括时间。日志时间戳建议精确到秒，日志时间的时区可以使用UTC或系统本地时区，该配置应当在用户手册中说明；
- 日志中必须包括日志级别，日志级别的定义见第3章日志级别。推荐在生产环境中打开INFO及以上级别日志，不推荐在生产环境中打开DEBUG级别日志；
- 日志中必须包含打印日志的文件及行数信息；
- 日志中必须包含当前进程的pid，在非敏感情况下推荐包含当前主机的ip；
- 日志中必须包含解释性信息，以给出记录该日志的具体原因。可以根据具体记录的需求添加多个字段，以提供更加全面的信息；
- 日志中禁止出现敏感信息，包括用户输入的密码、隐私信息等；
- 日志必须配置为可轮转的。推荐配置轮转周期为14天或以上，同时推荐配置为可根据日志文件大小进行轮转；
- 日志推荐配置为结构化的，以json格式输出；
- 日志推荐配置为可在运行时调整级别的，便于在出现问题时获取更详细的日志；
- 日志推荐完全使用英文

### 2.1格式样例
以下给出格式样例：
非结构化输出：
```
[<timestamp>] <level> <pid> <host_ip> <file>:<line> - <message> | <key1>=<value1> <key2>=<value2> ...
```

例子：
```
[2024-01-15T14:32:45+08:00] INFO 34521 10.244.3.128 inference_handler.go:342 - Inference request completed successfully | request_id=req_a1b2c3d4e5f6 model_name=llama2-70b engine=vllm input_tokens=256 output_tokens=512
```

结构化输出：
```json
{
  "timestamp": "2024-01-15T14:32:45+08:00",
  "level": "INFO",
  "pid": 34521,
  "host_ip": "10.244.3.128",
  "file": "inference_handler.go",
  "line": 342,
  "message": "Inference request completed successfully",
  "request_id": "req_a1b2c3d4e5f6",
  "model_name": "llama2-70b",
  "engine": "vllm",
  "input_tokens": 256,
  "output_tokens": 512
  }
```

### 2.2推荐使用的日志框架
Go：slog，预计在26.03版本社区会基于slog封装自己的日志库，基本保证调用兼容  
Python：Loguru

## 3 日志级别
日志推荐划分为：CRITICAL、ERROR、WARNING、INFO、DEBUG、TRACE六个级别，每个级别对应的范围如下表：
| 级别 | 解释 | 示例 |
| --- | --- | --- |
| CRITICAL | 系统即将崩溃或已经崩溃的严重错误，需要运维人员紧急处理。 | 无法恢复的致命异常、主进程启动失败。 |
| ERROR | 严重问题导致某个功能无法正常执行，部分功能失效，但是程序本身仍然可以正常运行。 | 文件读写异常、第三方API调用超时、环境依赖项不符合预期。 |
| WARNING | 潜在问题或不期望的情况，但不影响当前功能或错误可恢复。 | 使用了已废弃的API、即将达到资源限制（如磁盘空间80%）、API单次调用失败但重试后成功、函数传参错误。 |
| INFO | 重要的业务流程节点和状态变化。 | 重要配置加载、服务启动/停止。 |
| DEBUG | 详细的诊断信息，用于开发和调试。应当可以做到通过该级别日志诊断问题，而不依赖于进入生产环境进行调试。 | 函数入参和返回值、关键变量状态变化、条件分支判断结果、外部调用的请求/响应摘要。 |
| TRACE | 最细粒度的追踪信息，用于深度调试和性能分析。记录代码执行的每一个细节步骤。 | 循环每次迭代的详细信息、方法进入/退出时间戳、中间变量的逐步变化、底层协议报文原始数据、SQL执行计划、内存/对象生命周期追踪。 |

## 4 日志点
日志点是指一些程序中经常出现的、需要打印日志的位置。下面给出一些常见的日志点，并规定这些日志点的日志级别。
| 位置 | 级别 | 记录内容 | 示例 |
| --- | --- | --- | --- |
| API入口 | INFO | 请求参数、来源 | POST /orders, user_id=123 |
| API出口 | INFO | 响应状态、耗时 | 200 OK, duration=230ms |
| 业务开始 | INFO | 关键参数、业务类型 | Start checkout, cart_items=5 |
| 业务完成 | INFO | 结果ID、状态 | Order created: ORD123456 |
| 状态变更 | INFO | 变更前后状态 | Order status: PENDING → PAID |
| 外部调用前 | INFO/DEBUG | 目标服务、参数 | Calling payment API |
| 外部调用后 | INFO/WARNING | 响应码、耗时 | Payment API: 200, 1.2s |
| 必须退出的错误 | CRITICAL | 错误类型、退出原因、系统状态 | Out of memory, available=12MB, required=500MB, terminating |
| 严重错误 | ERROR | 堆栈、上下文 | Payment failed, order=123 |
| 可恢复错误 | WARNING | 错误类型、重试信息、降级策略 | Redis timeout, retrying 1/3, fallback to DB |
| 分支逻辑 | TRACE/DEBUG | 判断条件、结果 | Cache hit: true |
| 循环处理 | TRACE/DEBUG/INFO | 循环内使用TRACE/DEBUG记录详细信息，禁止使用INFO。循环结束使用INFO记录汇总信息 | Processed 1000/5000 |
| 资源操作 | INFO | 打开/关闭文件、连接 | Database connected |

## 5 最佳实践
本节记录部分日志相关的最佳实践，包括功能和性能方面的内容

### 5.1 禁止打印无意义日志
打印的日志必须包含上下文信息，禁止打印如“error 1”、“error 2”这类完全不携带任何信息的日志。

### 5.2 必须使用日志API输出日志
日志必须通过日志框架输出。直接调用printf、Println等系统API无法实现日志级别控制、日志收集等功能。且根据实现情况有可能会影响性能。

### 5.3 谨慎输出大量日志
输出大量日志可能会导致关键信息被覆盖，难以定位问题根因等。对于可能输出大量日志的情况，在代码设计时就需要考虑并处理，下面分几种具体情况给出指南：

#### 5.3.1 不推荐在循环中输出大量日志
循环中输出日志很容易在循环量大时导致日志刷屏，重复输出大量无效信息。循环当中打印正常代码流程相关信息不推荐高于DEBUG级，如果出现异常则遵循日志分级范围分级。同时可以在循环结束后使用INFO及以上级别输出关键信息。

#### 5.3.2 推荐对于完全相同的日志进行归类和累计
部分模块由于会被频繁调用，导致输出大量相同日志，可以考虑对相同或相似的日志做计数累积，输出重复次数。对于状态类日志，可以考虑仅在状态发生变化时记录日志。对于异常监控类日志，可以将正常情况的级别调低，主要记录异常情况和正常-异常转换的情况。

#### 5.3.3 推荐将日志合并在一条中输出
对于一处日志记录位置，推荐将所有需要记录的信息合并在一条日志中输出。

#### 5.3.4 推荐只输出必要的结构体信息
对于DEBUG级别以上的日志，不推荐将整个对象直接打印，而是筛选有关字段，避免因为结构体过大导致在日志中刷屏。

### 5.4 推荐在不可能发生的位置打印日志
对于代码中有多条分支或处理流较为复杂的情况，推荐在设计上无法到达（一般是最终兜底的default分支）的位置记录日志，帮助快速定位异常情况。

### 5.5 推荐限制日志单行长度
推荐单行日志长度不超过120个字符。
