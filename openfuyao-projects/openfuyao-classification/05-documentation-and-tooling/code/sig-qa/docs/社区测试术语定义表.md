# 社区测试术语定义表

本文档为 openFuyao 社区测试体系的术语统一定义，适用于测试方案、测试用例、测试报告及相关评审活动。所有测试相关文档应使用本表中的术语含义，避免歧义。

## 1. 测试层次与类型

| 术语 | 英文 | 定义 | 职责角色 | 备注 |
|------|------|------|----------|------|
| 单元测试（UT） | Unit Test | 针对代码中最小可测试单元（函数、方法、类）的测试，在IDE或简单Mock环境中执行，验证单元功能的正确性。应遵循FIRST原则（Fast/Isolated/Repeatable/Self-Validating/Thorough）。 | 开发者 | 孵化期特性UT覆盖率要求>40%，建议>80% |
| 开发者测试（DT） | Developer Test | 由开发者在开发阶段完成的测试活动的统称，包含单元测试和开发者编写的接口测试、组件级功能测试等。DT覆盖率以代码行覆盖率为度量依据。 | 开发者 | 成熟特性DT覆盖率要求>80%；孵化期特性>40% |
| 功能测试 | Functional Test | 一种黑盒测试，关注输入与预期输出，验证特性是否满足功能需求规格。不深入代码内部实现，以需求规格为判定依据。 | 特性SIG / QA SIG | 从SR粒度出发进行场景设计 |
| 冒烟测试 | Smoke Test | 对特性或版本的最基本功能进行快速验证的测试活动，执行P0级用例。冒烟测试不通过（P0用例失败）应打回给开发。 | 特性SIG / QA SIG | 每日构建通过率>95%；Beta/正式版本100% |
| 特性级集成测试 | Feature-level Integration Test | 特性所属各模块间的集成测试，在实际环境中验证特性内部各模块能够正确集成并实现需求。 | 特性SIG / 社区伙伴 | 关注模块间接口、协作行为、数据流 |
| 系统级集成测试 | System-level Integration Test | 将已确认的软件、硬件、外设、网络等元素结合在一起，在不同场景下验证整个系统是否满足预定的功能和非功能需求。有别于特性级集成测试，更关注组件在不同场景下的集成能力和系统整体稳定性、可用性。 | QA SIG / 社区伙伴 | 关注跨组件集成、不同OS/架构/K8s版本/硬件的兼容 |
| 专项测试 | Specialized Test | 针对特性非功能属性（DFX）开展的测试活动的统称，包括性能测试、安全测试、兼容性测试、可靠性测试、长稳测试、资料测试、一致性测试等。 | QA SIG / 特性SIG | 根据特性成熟度和版本要求确定必选/可选项 |
| 门禁测试 | Gate Test | PR提交后CI自动触发的检查，包括license检查、基本信息检查、接口变更检查、敏感信息检查等。 | Infra SIG / 特性SIG | 通过后方可进行镜像编译构建 |

## 2. 专项测试子类型

| 术语 | 英文 | 定义 | 关键指标 |
|------|------|------|----------|
| 性能测试 | Performance Test | 验证特性在时延、吞吐率、资源利用率、最大承受压力等方面是否满足性能规格。对非新增组件的特性，基线要求为"性能较上一版本不劣化"。 | 安装部署时间、接口时延、资源占用、吞吐率 |
| 安全测试 | Security Test | 按安全SIG规范对特性进行的安全验证，包括端口扫描、病毒扫描、漏洞扫描、代码扫描、SCA扫描等。须参照《产品网络安全红线》执行。 | CVE漏洞CVSS评分、安全编译选项、安全编码规范 |
| 兼容性测试 | Compatibility Test | 验证特性与不同操作系统、平台架构、Kubernetes版本、硬件设备、依赖组件版本的兼容能力。 | OS/架构/K8s版本/硬件兼容矩阵 |
| 可靠性测试 | Reliability Test | 验证特性的故障恢复能力，包括故障注入、异常场景恢复等。评估特性通过什么机制减少故障发生，以及对不同故障的表现是否符合预期。 | 故障恢复时间、故障场景覆盖率 |
| 长稳测试 | Long-term Stability Test | 7×24h持续运行测试，验证特性在长时间运行下的稳定性。孵化期特性报名参与，成熟期特性必须执行。 | 运行时长、性能劣化趋势、资源泄漏 |
| 资料测试 | Documentation Test | 以陌生用户视角对文档内容进行准确性审视，严格按照文档步骤执行操作，验证文档的正确性和可用性。 | 用户指南、开发指南、API参考的准确性 |
| 一致性测试 | Conformance Test | 验证实现是否符合标准规范的测试，QA SIG负责执行与用例管理，特性SIG负责用例维护。 | 标准符合率 |

## 3. DFX 属性定义

DFX（Design for X）表示面向产品非功能性属性的设计，X代表产品生命周期中的不同质量属性。测试方案设计应逐项评估以下DFX属性的适用性。

| 缩写 | 英文全称 | 中文名称 | 定义 | 测试要点 |
|------|----------|----------|------|----------|
| DFR | Design for Reliability | 可靠性设计 | 减少故障发生、降低故障影响、故障后尽快恢复 | 故障注入、异常恢复、长稳测试 |
| DFPf | Design for Performance | 性能设计 | 时延、吞吐率、资源利用率等系统性能 | 基线对比、压力测试、性能趋势分析 |
| DFT | Design for Testability | 可测试性设计 | 提高产品能观能控、故障检测与定位隔离的能力 | 日志完备性、监控可观测性、故障定位能力 |
| DFS | Design for Serviceability | 可服务性设计 | 提高安装调测与维护管理能力，含可维护性和易用性 | 安装部署、升级回退、运维操作 |
| DFNS | Design for Network Security | 安全性设计 | 机密性、完整性、可用性、访问控制、认证、隐私保护等 | 安全扫描、安全编码检查、安全合规报告 |
| DFC | Design for Compatibility | 兼容性设计 | 标准符合、互连互通、版本升级兼容 | 环境矩阵覆盖、升级验证 |
| DFEE | Design for Energy Efficiency | 能效与环境设计 | 能效与资源的有效利用，减少毒害性和资源消耗 | 资源消耗度量 |
| DFE | Design for Evolution | 可演进性设计 | 对不同场景和未来需求的灵活应对能力 | 接口扩展性、配置灵活性 |

## 4. 测试用例等级

| 等级 | 名称 | 定义 | 占比参考 |
|------|------|------|----------|
| P0 | 冒烟级 | 最基本的功能验证：安装、卸载、核心功能的正向主流程 | 约5% |
| P1 | 基本功能级 | 基本功能验证：继承特性的基本功能、迭代验收前的基本功能验证、需求的绝大部分规格覆盖 | P0+P1合计约15%~20% |
| P2 | 重要特性级 | 重要特性验证：不影响核心功能的前端页面功能、DFX属性（兼容性、可靠性、简单性能验证） | — |
| P3 | 一般功能级 | 一般功能/非重要功能验证：包括对基本/重要功能的异常测试 | — |
| P4 | 特殊场景级 | 非常特殊的输入、场景、阈值条件的用例 | 社区测试基本不涉及 |

**转测验收要求：** 所有P0/P1级用例必须执行并通过，未通过用例需有issue跟踪。

## 5. 测试度量指标

| 术语 | 定义 | 参考值 |
|------|------|--------|
| DT覆盖率 | 开发者测试的代码行覆盖率 | 成熟特性>80%，孵化期>40% |
| 用例密度 | 每千行代码（KLOC）对应的测试用例数 | 目标26.3，下限15.7，上限36.8 |
| 缺陷密度 | 平均执行多少个测试用例发现1个缺陷 | 目标4.3，区间[2.6, 6.1] |
| 测试用例通过率 | 通过的用例数 / 总用例数 | Beta>95%，正式版本100% |
| 自动化率 | 自动化执行的用例数 / 总用例数 | 转测一周内要求>80% |
| 冒烟测试通过率 | P0用例通过数 / P0用例总数 | 每日构建>95%，Beta/正式版100% |

## 6. 测试流程术语

| 术语 | 定义 |
|------|------|
| 转测 | 特性需求开发达到可支撑测试的完成度后，由开发向测试移交进行验证的过程。通过全部P0/P1用例后视为通过转测验收。 |
| 转测验收 | 测试收到转测后对特性进行的初步验证（一般3个工作日），P0/P1用例不通过或验出严重阻塞问题可直接打回。 |
| 打回 | 转测验收不通过，将特性退回开发修复后重新转测。触发条件：P0/P1不通过、严重阻塞问题、验收期内严重问题未闭环、DT覆盖率不达标（v26.06起）。 |
| RC版本 | Release Candidate，社区定期发布的联调版本，供社区伙伴进行特性试用与联调验证。 |
| daily build | PR合入后CI自动构建的每日版本，通过门禁检查后发布。 |
| 测试左移 | 在软件开发生命周期的早期就开始测试活动，测试不是开发完成后才进行的活动，而是开发过程的内在组成部分。 |

## 7. 测试角色术语

| 术语 | 定义 |
|------|------|
| 测试Owner | 负责某特性测试的人员，对该特性质量负责。特性质量对时间的妥协可由任何人提出，唯独不可以是测试Owner自己。 |
| QA接口人 | 特性SIG中负责与QA SIG沟通的联系人，看护SIG内各测试任务的规划与进度，定期汇报测试进展。应相对稳定，至少覆盖一个完整版本周期。 |
| 特性SIG | 负责特性开发及UT/DT、功能测试、特性级集成测试、部分专项测试的SIG组。 |
| QA SIG | 负责社区发行版的系统级集成测试、专项测试支持、版本整体测试管理的SIG组。 |

## 8. 问题分级

| 级别 | 功能维度 | 性能维度 | 安全维度 |
|------|----------|----------|----------|
| 严重 | 阻塞基础测试，导致核心组件或扩展组件不能提供正常服务 | 性能测试结果低于规格30%及以上 | 存在CVSS 9分及以上CVE漏洞未修复 |
| 主要 | 需求明确要求的功能未实现或实现不正确，造成特性无法满足需求；或阻塞组件基础测试但不影响其他组件 | 性能低于规格20%~30%；或长时间测试性能下降趋势明显（下降幅度≥5%） | CVSS 7~9分CVE未修复；存在病毒木马；安全基线用例未通过；开源片段引用或License不合规 |
| 次要 | 规格实现有问题但未造成整个特性失效；或阻塞模块功能测试但不影响基础功能 | 性能低于规格10%~20%；或长时间测试性能下降幅度0%~5% | CVSS 4~7分CVE未修复；安全编译选项未使用；安全编码问题 |
| 不重要 | 拼写等UCD错误；易用性问题；功能优化建议 | 性能低于规格0%~10% | CVSS 0~4分CVE未修复 |

## 9. 其他术语

| 术语 | 定义 |
|------|------|
| IR | Integration Requirement，集成需求，特性级别的需求编号 |
| SR | Sub Requirement，子需求，IR下细分的需求项 |
| AR | Atomic Requirement，原子需求，SR下进一步拆分的最小需求单元 |
| CRD | Custom Resource Definition，Kubernetes自定义资源定义 |
| CR | Custom Resource，基于CRD创建的自定义资源实例 |
| SCA | Software Composition Analysis，软件成分分析 |
| CVSS | Common Vulnerability Scoring System，通用漏洞评分系统 |
| E2E可追溯 | 需求端到端可追溯，从需求→代码、需求→用例、用例→缺陷、代码→缺陷可追溯，所有变更受控并有记录 |
| 正交因子 | 影响测试结果的独立变量，通过正交试验法组合不同因子取值以高效覆盖测试场景 |
| 特性规格 | 特性开发到什么程度算满足需求的完整描述，包含功能需求和DFX需求 |
